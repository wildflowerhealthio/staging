Grant Flows

Covers authorization-server-rust/tests/integration/grant_flows.rs

These tests hold the server to its main promise: an app reaches the Owner’s FHIR server only after the Owner said yes, now or in a standing grant, and never with more than the Owner and the browser it runs in hold. They drive the whole authorization-code flow over HTTP, from /oauth/authorize to /oauth/token, so this page starts with that flow as a story. The entities it moves through have their own pages: the code request, the grant, the authorization code, the browser session and the client.

The story

The Owner has paired their laptop browser. They open Wildflower Strength, a SMART app, in that browser. Strength asks for patient/Observation.rs and launch/patient.

The front door: no session, no request

The browser lands on GET /oauth/authorize. The first check is about the browser, not the app: does it carry a browser session?

#![allow(unused)]

A code is always issued under a browser session (its sid). Without one there is nothing to issue under and nothing to revoke later, so the browser is sent to pair first, with this request’s path and query as where to come back to. Nothing is written yet, so the detour spends no SMART launch value.

Everything after this point runs in one write scope, in CodeAuthorizationStarter::start. Telling the Owner’s popup about a new request happens after the scope closes.

Three questions decide where the browser goes

The starter first validates the request: a signing key to mint with, a client that isn’t disabled, PKCE, and the client’s registration. A server-defined registration holds the request to its redirects and scopes. Any other client is trusted on first use: whatever steps outside its registration is carried to the Owner as a presented client change. Then three questions about the request pick the next step:

The second half of waits_on_limited_page means the limited page is shown once per browser per app: once this browser has pressed Continue for Strength, its later Strength requests skip the page, whatever the session lacks. Every one of these paths, the fast path included, parks a code request first. From then on the request changes only through its own transitions, each written as a guarded replace on its status (the Authorization Request page), so the first decision wins.

The Owner decides

Strength’s request is pending. The laptop isn’t the Owner, so it went to the wait page, and the host app on the Owner’s phone shows the request as the Owner prompt. authorization-server-rust/src/domain/capabilities/access/consents/oauth.rs lines 200–223 · authorization-server in the code index

You can’t give away what you don’t hold. DelegatedScopes::clamp is the whole rule:

  1. The approver must hold the prompt’s approval scopes: the power to decide a request, to record a grant, to write the registration of a client trusted on first use, and every resource scope (or wildflower/launch) the request asks for. Missing any is a 403 that names them, whatever was ticked (Approval Scopes).
  2. The ticks are clamped to what the prompt may grant: each must be covered by a requested scope and by the client’s registration, which for a client trusted on first use takes in what it asked for.
  3. Every resource scope that survives must be covered by the approver’s own grant.

If nothing survives, the request is denied. Before that, a request that would change the app’s registration needs the Owner to acknowledge so (a 409 otherwise). And when the SMART launch pinned a patient, the approval must name that patient (CodeRequest::admits_patient).

Three rules, in the order they run:

  1. The requesting browser must still be live. If the laptop was signed out while the Owner decided, the approval becomes a denial and Strength hears access_denied. There’s no session left to issue under.
  2. The request records what the authority allowed (the approval’s granted scopes): the Owner’s delegated scopes, or the requested scopes the standing grant covered (CodeRequest::approve).
  3. The code carries that, intersected with the browser’s session (session_bounded_scopes). A browser paired read-only earns its apps read-only access, whoever approved. The code also carries the sid, so revoking the laptop later ends everything Strength earned there.

On the Owner’s path, the same write scope then records the grant for (Strength, its redirect), unioned into any grant already there, and for a client trusted on first use creates or widens its registration (GrantRecorder::record_code_grant). The code, the grant and the registration land together or not at all. The grant is what lets the next request’s second question answer yes. On the fast path, the same scope stamps the standing grant’s last_used_at instead.

authorization-server-rust/src/domain/capabilities/oauth/code_authorization_starter.rs lines 616–628 · authorization-server in the code index

GrantCoverage::resolve answers Full only when the request makes no change to the client’s registration (its presented client change is NoChange) and the standing grant for that client and redirect covers every requested scope. Coverage is by permission, not spelling (allowed_scope_covers): a grant for patient/Observation.rs answers a request for patient/Observation.r. A request that is new or steps outside the registration never takes the fast path, however well an old grant covers it: the Owner hasn’t seen that combination. The browser session’s part was settled by the first question: a request still waiting on its limited page never gets this far.

Redemption: the code is spent once

The browser is sent back to Strength’s redirect with ?code=…&state=…. Strength posts the code and its PKCE verifier to /oauth/token, which builds the proof RedeemedAuthorizationCode:

authorization-server-rust/src/domain/authority/redemption.rs lines 192–202 · authorization-server in the code index

A code presented twice means someone else has seen it. The second presentation fails, and it also expires every refresh family the first redemption started. The attacker gets nothing, and the real app has to ask again.

The code is consumed before its bindings are checked: same client, same redirect, not expired, and the PKCE verifier matching the challenge. A code that fails any of them is spent all the same, and every failure reads invalid_grant on the wire. The token then carries the code’s scopes, which the session already bounded. Its scope claim adds each SMART scope’s other spelling (with_alternate_canonical_forms), so the FHIR server can read either.

Where the story lands

Follow the scopes and each step can only narrow them:

asked for      ∩ registration           → approvable          (the Owner decides)
approvable     ∩ Owner's ticks, ⊆ Owner → DelegatedScopes     (the Owner decides)
DelegatedScopes                         → Approval on request (approving: the record)
DelegatedScopes ∩ browser session       → code's scopes       (approving: what's issued)
code's scopes                           → token's scopes      (redemption)

On the fast path the standing grant’s coverage stands in for DelegatedScopes. When you review a change to this crate, ask which arrow it touches. If it touches none, it shouldn’t be able to change what anyone can access. If it touches one, the proof or writer at that arrow is where to look.

integration::grant_flows

auth_code_grant_happy_path_end_to_end

An app the Owner approves ends up with a signed bearer token for exactly the approved scope: /oauth/authorize parks the browser on the wait page, the Owner approves, the approve response and the wait page’s poll hand back the same code (the poll’s answer uncached), and /oauth/token redeems it. No offline_access was granted, so no refresh token comes back.

#![allow(unused)]
fn main() {
async fn auth_code_grant_happy_path_end_to_end() {
    let (g, owner_token, db) = spin_up();
    seed_client_with_redirect(&db, "test-app", "https://app.example/cb", &["read"]);
    let challenge = compute_code_challenge(CODE_VERIFIER);

    // 1. /authorize parks a pending request and 302s to the wait page.
    let query = format!(
        "response_type=code&code_challenge_method=S256&client_id=test-app&scope=read&\
         code_challenge={challenge}&redirect_uri=https%3A%2F%2Fapp.example%2Fcb&state=xyz"
    );
    let res = g
        .router
        .clone()
        .oneshot(build_request(
            Request::get(format!("/oauth/authorize?{query}"))
                .header("cookie", browser_session_cookie(&db.paired_browser_token)),
            Body::empty(),
        ))
        .await
        .expect("oneshot");
    assert_eq!(res.status(), StatusCode::FOUND);
    let polling = res
        .headers()
        .get("location")
        .and_then(|v| v.to_str().ok())
        .expect("location")
        .to_string();
    let request_id = polling_request_id(&polling);

    // 2. Owner approves the requested scope via the consent endpoint.
    let approve = build_request(
        Request::post(format!(
            "/authorization/oauth-consents/{request_id}/approve"
        ))
        .header("host", "127.0.0.1")
        .header("authorization", format!("Bearer {owner_token}"))
        .header("content-type", "application/json"),
        Body::from(r#"{"approvedScopes":["read"],"acknowledgedRegistrationChange":false}"#),
    );
    let res = g.router.clone().oneshot(approve).await.expect("oneshot");
    assert_eq!(res.status(), StatusCode::OK);
    // The approve response's inline-completion redirect must target the client's
    // `redirect_uri` and carry both the redeemable `code` and the client's `state`.
    let approve_body = body_json(res.into_body()).await;
    assert_eq!(approve_body["status"], "approved");
    let approve_redirect = approve_body["redirect"].as_str().expect("approve redirect");
    assert!(
        approve_redirect.starts_with("https://app.example/cb"),
        "approve redirect should target the client redirect_uri, got {approve_redirect}"
    );
    let (approve_code, approve_state) = {
        let url = Url::parse(approve_redirect).expect("approve redirect url");
        let code = url
            .query_pairs()
            .find(|(k, _)| k == "code")
            .map(|(_, v)| v.into_owned())
            .expect("approve code param");
        let state = url
            .query_pairs()
            .find(|(k, _)| k == "state")
            .map(|(_, v)| v.into_owned())
            .expect("approve state param");
        (code, state)
    };
    assert_eq!(approve_state, "xyz");

    // 3. The status poll now reports Approved and hands back the client
    //    redirect carrying the redeemable `code`. It must agree with the code
    //    the approve response already returned.
    let res = get_authorization_status(&g.router, &db.paired_browser_token, &request_id).await;
    assert_eq!(res.status(), StatusCode::OK);
    // The Approved redirect carries a redeemable code, so no cache may keep it.
    assert_cache_suppressed(&res, "the Approved status poll");
    let status = body_json(res.into_body()).await;
    assert_eq!(status["status"], "approved");
    let redirect = status["redirect"].as_str().expect("redirect");
    let code = Url::parse(redirect)
        .expect("redirect url")
        .query_pairs()
        .find(|(k, _)| k == "code")
        .map(|(_, v)| v.into_owned())
        .expect("code param");
    assert_eq!(
        code, approve_code,
        "approve-response code and poll code must agree"
    );

    // 4. /token redeems the code with the matching PKCE verifier.
    let body = format!(
        "grant_type=authorization_code&client_id=test-app&code={code}&\
         code_verifier={CODE_VERIFIER}&redirect_uri=https%3A%2F%2Fapp.example%2Fcb"
    );
    let res = g
        .router
        .clone()
        .oneshot(build_request(
            Request::post("/oauth/token")
                .header("content-type", "application/x-www-form-urlencoded"),
            Body::from(body),
        ))
        .await
        .expect("oneshot");
    assert_eq!(res.status(), StatusCode::OK);
    let token = body_json(res.into_body()).await;
    assert_eq!(token["token_type"], "Bearer");
    assert_eq!(token["scope"], "read");
    assert!(!token["access_token"]
        .as_str()
        .expect("access_token")
        .is_empty());
    // No `offline_access` in the grant → no standing credential.
    assert!(token.get("refresh_token").is_none());
}
}

The whole trust-on-first-use loop: an acknowledged approval registers the app (public client, named by its id, the one redirect it used, the granted scopes), issues the code, and leaves a standing grant — so the same request a moment later is registered and takes the fast path straight back to the client.

async fn approving_a_new_app_registers_it_and_the_next_request_fast_paths() {
    let (g, owner_token, db) = spin_up();

        &g.router,
        &db.paired_browser_token,
        &authorize_query("brand-new-app", "read"),
    )
    .await;
    let request_id = parked_request_id(&res);

    let res = approve_oauth_consent(
        &g,
        &owner_token,
        &request_id,

    .await;

        .unwrap()
        .is_some());

approving_a_changed_app_widens_its_registration

Approving a known client’s changed request widens its registration in place: the new redirect is appended to the existing allowlist, the granted scopes are unioned, a requested-but-pruned scope is NOT added, and the row’s identity (registered_at, name) survives.

async fn approving_a_changed_app_widens_its_registration() {
    let (g, owner_token, db) = spin_up();

    let store = store_handle(&db);
    let before = store
        .read(|tx| tx.client_by_id("test-app"))
        .unwrap()
        .unwrap();

    // A different redirect AND two scopes the registration doesn't cover.
    let res = get_authorize(
        &g.router,
        &db.paired_browser_token,

    let consent = get_oauth_consent(&g, &owner_token, &request_id).await;
    assert_eq!(
        consent["registration"],
        serde_json::json!({
            "status": "changed",
            "redirectUriIsNew": true,
            "newScopes": ["write", "pruned"],
        }),
    );

    let res = approve_oauth_consent(
        &g,
        &owner_token,
        &request_id,

    assert_eq!(
        after.allowed_scopes,
        vec!["read".to_string(), "write".to_string()],
    );
    assert_eq!(after.name, before.name);
    assert_eq!(after.registered_at, before.registered_at);

a_changed_request_never_takes_the_fast_path

The fast path is gated on the presented client change, not on grant coverage alone: once the registration no longer covers the request, a standing grant that does cover every requested scope doesn’t skip the Owner, who has not seen this combination.

#![allow(unused)]
fn main() {
async fn a_changed_request_never_takes_the_fast_path() {
    let (g, owner_token, db) = spin_up();
    seed_client_with_redirect(&db, "test-app", "https://app.example/cb", &["read"]);
    authorize_and_approve(
        &g,
        &owner_token,
        &db.paired_browser_token,
        "test-app",
        "read",
        r#"{"approvedScopes":["read"],"acknowledgedRegistrationChange":false}"#,
    )
    .await;

    // The grant now covers `read`; narrow the registration out from under it.
    let store = store_handle(&db);
    let mut client = store
        .read(|tx| tx.client_by_id("test-app"))
        .unwrap()
        .unwrap();
    client.allowed_scopes = Vec::new();
    store
        .write(|tx| tx.upsert_client(&client))
        .expect("narrow the client");

    let res = get_authorize(
        &g.router,
        &db.paired_browser_token,
        &authorize_query("test-app", "read"),
    )
    .await;
    let request_id = parked_request_id(&res);
    let consent = get_oauth_consent(&g, &owner_token, &request_id).await;
    assert_eq!(consent["registration"]["status"], "changed");
    // The pre-approved set is empty too: a changed request is presented fresh.
    assert_eq!(
        consent["preApprovedScopes"],
        serde_json::json!([] as [&str; 0])
    );
}
