Same-Device Sign-In

Covers authorization-server-rust/src/domain/capabilities/oauth/same_device_sign_in.rs

The Owner’s own browser doesn’t pair. The base app, running on the same device as the server, mints a one-time sign-in code in-process and opens GET /oauth/sign-in?code=…&next=… in a browser. Only the base can mint a code, so redeeming one proves the browser is on the Owner’s device. The sign-in starts a same-device browser session holding the Owner’s scopes, hands the browser that session’s token for its cookie, and sends it on to next.

The codes live in memory, not in the store, and redeeming one takes it out for good, even when the write scope later rolls back. So everything that can refuse a sign-in without the code’s fault runs before the code is touched, and a refused next or a disabled client leaves the code redeemable. A failure after the code is taken spends it: if the session can’t be stored or the token can’t be minted, no session remains, and signing in again takes a new code. Before the session’s write scope commits, the codes remember it by the code that started it, so the base can end it once the server’s launch views have closed, and no session lands that its code doesn’t find. A code the base withdrew before then, as its view closed, signs nobody in: the scope rolls back and the token is never handed out, so a closed view’s late sign-in can’t replace the cookie a view still open holds.

The redemption is the RedeemedSameDeviceSignInCode proof; the browser session writer stores the session it carries, and the access token minter signs its token.

The tests sign in over the sign-in fixtures.

sign_in

Where a sign-in may go next is the sign-in destinations.

Redeem presented_code at now for a same-device session and its token, both lasting SAME_DEVICE_SESSION_TTL, to go on to next. A next that isn’t allowed, or a disabled browser-session client, is refused before the code is touched, so the code stays redeemable. The session is stored and its token signed in one write scope, which also has the codes remember the session by the code before it commits, so the base can end it once the view it opened closes, and no session lands that its code doesn’t find. A code the base withdrew before then, as its view closed, signs nobody in: the scope rolls back, and the token is never handed out. A failure after this call takes the code spends it: the code leaves memory even when the scope rolls back, so signing in again takes a new code. A failure before then leaves the code as it stood, so a second presentation of a code mid-sign-in can’t clear its withdrawal.

Errors

SameDeviceSignInError::Refused for a next that isn’t allowed (SignInRefusal::RedirectNotAllowed), a disabled browser-session client (SignInRefusal::BrowserSessionClientDisabled), or a code that is unknown, spent, expired or withdrawn (SignInRefusal::CodeNotRedeemable); SameDeviceSignInError::Store when the browser-session client can’t be read; SameDeviceSignInError::SessionNotStored when the session can’t be stored; SameDeviceSignInError::Issuance when minting fails.

#![allow(unused)]
fn main() {
pub(crate) fn sign_in(
    &self,
    presented_code: &str,
    next: &str,
    now: DateTime<Utc>,
) -> Result<SignedIn, SameDeviceSignInError> {
    let redirect = self
        .destinations
        .allow(next)
        .ok_or(SameDeviceSignInError::Refused(
            SignInRefusal::RedirectNotAllowed,
        ))?;
    let mut code_taken = false;
    let stored = self.store.write(|tx| {
        if is_browser_session_client_disabled(tx)? {
            return Err(SameDeviceSignInError::Refused(
                SignInRefusal::BrowserSessionClientDisabled,
            ));
        }
        let redeemed_sign_in_code = RedeemedSameDeviceSignInCode::redeem(
            &self.codes,
            presented_code,
            &self.owner_grant,
            SAME_DEVICE_SESSION_TTL,
            now,
        )
        .ok_or(SameDeviceSignInError::Refused(
            SignInRefusal::CodeNotRedeemable,
        ))?;
        code_taken = true;
        BrowserSessionWriter::within(tx)
            .start_same_device_session(&redeemed_sign_in_code)
            .map_err(SameDeviceSignInError::SessionNotStored)?;
        let session_token = AccessTokenMinter::with_active_key(
            tx,
            &self.server_origin,
            SAME_DEVICE_SESSION_TTL,
        )
        .and_then(|minter| {
            minter.mint(TokenEntitlement::SameDeviceSignIn(&redeemed_sign_in_code))
        })
        .map_err(SameDeviceSignInError::Issuance)?;
        if !self
            .codes
            .session_stored(presented_code, redeemed_sign_in_code.session())
        {
            return Err(SameDeviceSignInError::Refused(
                SignInRefusal::CodeNotRedeemable,
            ));
        }
        Ok(session_token)
    });
    let session_token = match stored {
        Ok(session_token) => session_token,
        Err(error) => {
            if code_taken {
                self.codes.session_not_stored(presented_code);
            }
            return Err(error);
        }
    };
    Ok(SignedIn {
        session_token,
        redirect,
    })
}
}

fn a_code_withdrawn_before_its_scope_commits_finds_its_session() {

is_browser_session_client_disabled

Whether the browser-session client is disabled. It is an essential client, which the Owner can’t disable, so only a row disabled out of band (direct SQL) is. Its row is seeded at boot, so a missing one is an error, not an enabled client.

#![allow(unused)]
fn main() {
fn is_browser_session_client_disabled(
    tx: &mut impl ClientsTx,
) -> Result<bool, AuthorizationServerError> {
    let browser_session_client = tx.client_by_id(BROWSER_SESSION_CLIENT_ID)?.ok_or_else(|| {
        AuthorizationServerError::ClientNotFound {
            client_id: BROWSER_SESSION_CLIENT_ID.to_owned(),
        }
    })?;
    Ok(browser_session_client.disabled_at.is_some())
}
}
