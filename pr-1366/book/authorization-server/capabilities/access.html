Access

Covers authorization-server-rust/src/domain/capabilities/access/mod.rs

The /authorization surface is where the server is administered: the Owner’s UI decides a consent prompt, lists the standing grants and revokes one, disables an app, signs a browser out, revokes a token. A paired browser reaches the same surface, holding less. What a caller may do here is exactly what its token’s scopes cover. The scopes are Wildflower resource scopes (wildflower/Grant.r to read the grants, wildflower/Grant.d to revoke one), and the Owner’s token carries wildflower/*.cruds, which covers every one of them.

The Scoped<…> extractor

A handler on this surface takes its capability as Scoped<…>, never the store. The extractor reads the verified claims the bearer gate left on the request, checks that they cover every scope the capability requires, and only then builds the capability. A token short of a scope gets a 403 naming the scopes it lacks, and the handler never runs.

#![allow(unused)]
fn main() {
let required_scopes = F::required_scopes();
// An empty fixed requirement is the same kind of wiring bug: it would
// admit any authenticated caller while looking gated — fail closed.
if F::REQUIRES_SCOPES && required_scopes.is_empty() {
    return Err(InternalError::new(
        "scoped capability",
        "a FixedScopeCapability must require at least one scope; make the \
         capability data-dependent (impl Capability directly, storing the \
         Grant) if its check is per-resource",
    )
    .into_response());
}
let granted = claims.granted();
let missing: Vec<Scope> = required_scopes
    .into_iter()
    .filter(|required| !granted.covers(required))
    .collect();
if missing.is_empty() {
    Ok(Scoped(F::build(state.clone(), granted)))
} else {
    Err(F::Error::from(MissingScopes::uncovered(&missing)).into_response())
}
}

The extractor and its traits are shared with other slices, in the scope-capabilities crate. A capability comes in one of two flavours:

  • Fixed-scope: one static scope set gates the whole capability. Most capabilities here are this flavour.
  • Data-dependent: the static gate admits the caller, and the capability keeps the caller’s own grant to check more on each call. The consent reader and decider are this flavour, since approving a request takes scopes that depend on the request (the approval scopes).

Each capability’s file declares its gate as a *_scopes() function, which the capability’s binding enforces:

grantable_admin_scopes

Each scope this surface checks is spelt in exactly one place, its *_scopes() function, and this list reads every one of them, so what a token can be given and what it is checked against can’t drift apart. A misspelt scope would parse as an unknown scope that the Owner’s wildflower/*.cruds can’t cover, locking the Owner out of that route; the second test rules that out.

The admin scopes the /authorization surface enforces, deduplicated in declaration order — the registry mapping capability → required scope. Because it reads the very *_scopes() functions the Capability bindings enforce, what a token can be granted and what it is checked against come from one source. Exported as the intended vocabulary for the consent surfaces; nothing consumes it yet (the tests below pin it until the consent UI does).

#![allow(unused)]
fn main() {
pub fn grantable_admin_scopes() -> Vec<Scope> {
    let declared = [
        grants::grants_reader_scopes(),
        grants::grants_revoker_scopes(),
        clients::clients_reader_scopes(),
        clients::clients_disabler_scopes(),
        consents::consent_reader_scopes(),
        consents::consent_decider_scopes(),
        consents::grant_creating_approval_scopes(),
        consents::client_registering_approval_scopes(),
        tokens::token_revoker_scopes(),
        browser_sessions::browser_sessions_reader_scopes(),
        browser_sessions::browser_sessions_revoker_scopes(),
    ];
    let mut seen = HashSet::new();
    declared
        .into_iter()
        .flatten()
        .filter(|scope| seen.insert(scope.clone()))
        .collect()
}
}

#![allow(unused)]
fn main() {
fn every_required_scope_is_a_known_wildflower_resource_not_unknown() {
    // A typo in a required-scope spelling would fall to `Scope::Unknown`,
    // which an owner's `wildflower/*.cruds` can't cover — locking the owner
    // out. Assert each is a real Wildflower resource scope so that can't ship.
    for scope in grantable_admin_scopes() {
        assert!(
            matches!(scope, Scope::WildflowerResource(_)),
            "required scope {scope} is not a wildflower resource scope",
        );
    }
}
}

authorization-server-rust/src/domain/capabilities/access/mod.rs lines 96–106 · authorization-server in the code index

Registry-completeness guard: every scope a capability checks is declared by one *_scopes() function (a capability’s gate, or a per-call requirement such as the consent approval scopes), and grantable_admin_scopes’s declared array must list all of them. A scope checked without registering is one the grantable vocabulary never offers — a silent lock-out. Counting the scope functions textually keeps honest additions honest.

#![allow(unused)]
fn main() {
fn every_capability_scope_fn_is_registered_in_the_grantable_vocabulary() {
    const CAPABILITY_SOURCES: &[&str] = &[
        include_str!("grants.rs"),
        include_str!("clients.rs"),
        include_str!("consents/mod.rs"),
        include_str!("tokens.rs"),
        include_str!("browser_sessions.rs"),
    ];
    let scope_fns: usize = CAPABILITY_SOURCES
        .iter()
        .map(|source| source.matches("_scopes() -> Vec<Scope>").count())
        .sum();
    // One `declared` entry per scope function. Update BOTH when adding a
    // checked scope: its `*_scopes()` fn and the `declared` array.
    let declared_entries = 11;
    assert_eq!(
        scope_fns, declared_entries,
        "found {scope_fns} capability scope functions but grantable_admin_scopes() declares \
         {declared_entries}; register the new capability in its `declared` array",
    );
}
}
