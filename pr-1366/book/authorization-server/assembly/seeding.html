Wildflower, Read in Order

Seeding

Covers authorization-server-rust/src/seeding.rs

Some rows must exist before anyone can ask for anything: a key to sign tokens with, and the server’s own clients. Seeding writes them at every boot, and is safe to run again. The signing key is inserted only when no key is active, and never rotated. The server’s own clients are upserted: rewritten to match the code every boot, so their registrations follow the host’s configuration and a store written by another build is corrected. An upsert keeps a row’s registration time and any disable the Owner set.

The bundled SMART sample apps’ clients are static, so a migration seeds them instead (0003_seed_sample_clients). Seeding in code is kept for what depends on the running host: the configured scopes and origin, and a freshly generated key.

A debug build also seeds a client for each first-party app’s local dev server. Release builds contain no code that could write them.

seeding

First-boot seeding for the grant store: the signing key and the essential clients (the host app’s client and the browser-session client). Safe to call on every boot — the signing key is inserted only when none exists (never rotated), and the two clients are ensured (re-applied as an upsert) so their definitions always match the host’s granted scopes, correcting any drift in the stored rows.

The bundled SMART sample-app clients (growth-chart, medication-viewer → my_web_app, PRECISE-HBR) are seeded in SQL instead — migration 0003_seed_sample_clients — since they’re static definitions a migration can express. Only the runtime-derived seeds (the essential clients’ scopes, the generated signing key) stay here.

open_and_seed_store

setup_authorization_server calls it first, and the server doesn’t start if it fails. A key is generated before the write scope opens, because generating an RSA key is slow.

Wrap the host-owned connection pool in a grant store (applying migrations, which includes the SQL seed of the SMART sample-app clients) and run the runtime-derived first-boot seeding steps — the signing key, the essential clients, and the FHIR server UI’s client. Safe to call on every boot.

Errors

Returns an error if the store cannot be created (migrations) or if any seeding step fails.

#![allow(unused)]
fn main() {
pub fn open_and_seed_store(
    pool: DieselPool,
    host_app_client_scopes: &[String],
    fhir_ui_client_id: &str,
    server_origin: &url::Url,
) -> anyhow::Result<SqliteGrantStore> {
    let store = SqliteGrantStore::new(pool).context("failed to open grant store")?;
    // RSA key generation is slow, so it runs before the write lock is taken,
    // and only on a boot that finds no active key.
    let candidate_signing_key = if store
        .read(|tx| tx.active_signing_key())
        .context("failed to read signing keys")?
        .is_none()
    {
        Some(SigningKey::generate().context("failed to generate signing key")?)
    } else {
        None
    };
    store.write(|tx| -> anyhow::Result<()> {
        ensure_some_active_signing_key(tx, candidate_signing_key)
            .context("failed to seed signing key")?;
        ensure_essential_clients(tx, host_app_client_scopes)
            .context("failed to seed the essential clients")?;
        ensure_fhir_ui_client(tx, fhir_ui_client_id, server_origin)
            .context("failed to seed the FHIR server UI client")
    })?;
    Ok(store)
}
}

ensure_some_active_signing_key

Insert candidate, generated before the scope opened, as the active signing key if none is active; otherwise leave the existing keys alone. Idempotent — safe to call on every boot.

#![allow(unused)]
fn main() {
fn ensure_some_active_signing_key(
    tx: &mut impl SigningKeysTx,
    candidate: Option<SigningKey>,
) -> anyhow::Result<()> {
    let existing = tx.active_signing_key().context("read signing keys")?;
    if existing.is_some() {
        return Ok(());
    }
    let mut key = candidate.context("the active signing key vanished during seeding")?;
    key.is_active = true;
    tx.insert_signing_key(&key).context("insert signing key")?;
    Ok(())
}
}

ensure_essential_clients

The two essential clients are server-defined, public, and have no redirect URIs. The browser-session client has no grant type: its tokens are minted only at /oauth/sign-in and by the pairing page’s poll, and neither is an OAuth flow.

Ensure the essential clients — the host app’s client (crate::WILDFLOWER_HOST_APP_CLIENT_ID) and the browser-session client (crate::BROWSER_SESSION_CLIENT_ID) — match the code’s definitions. Upserted on every boot so their policy always matches: the host app’s client is allowed host_app_client_scopes (the live app sources them from tauri-shared-config.json; see crate::default_host_app_client_scopes), and the browser-session client the Owner’s scopes (crate::OWNER_SCOPES), the most any browser session may hold. This corrects stored rows that have drifted (registration time and any admin disable are preserved).

Both are public with no redirect URIs. The host app’s client is allowed every grant type; the browser-session client none, since its tokens are minted only at /oauth/sign-in (a same-device session) and by the pairing page’s poll (a paired session), neither of them OAuth, so no OAuth flow can be run as it and /oauth/token never mints its token.

#![allow(unused)]
fn main() {
fn ensure_essential_clients(
    tx: &mut impl ClientsTx,
    host_app_client_scopes: &[String],
) -> anyhow::Result<()> {
    let wildflower_host_app_client = Client {
        client_id: crate::WILDFLOWER_HOST_APP_CLIENT_ID.to_string(),
        name: "Wildflower Host".to_string(),
        kind: ClientKind::Public,
        redirect_uris: vec![],
        allowed_scopes: host_app_client_scopes.to_vec(),
        allowed_grant_types: AllowedGrantType::ALL.to_vec(),
        secret_hash: None,
        registered_at: Utc::now(),
        disabled_at: None,
        registration_source: RegistrationSource::ServerDefined,
    };
    tx.upsert_client(&wildflower_host_app_client)
        .context("seed the host app's client")?;
    let browser_session_client = Client {
        client_id: crate::BROWSER_SESSION_CLIENT_ID.to_string(),
        name: "Wildflower Browsers".to_string(),
        kind: ClientKind::Public,
        redirect_uris: vec![],
        allowed_scopes: crate::owner_scopes(),
        allowed_grant_types: vec![],
        secret_hash: None,
        registered_at: Utc::now(),
        disabled_at: None,
        registration_source: RegistrationSource::ServerDefined,
    };
    tx.upsert_client(&browser_session_client)
        .context("seed the browser-session client")?;
    Ok(())
}
}

seed_dev_app_clients

Debug builds only: a client for each first-party app’s local dev server. The first-party apps ship from the published site, and their clients register its redirect. A debug build also gets a dev tile per app, whose launch URL points at the app’s vite dev server on localhost, and that launch needs a client whose redirect is that exact loopback address. Each dev client is a separate client under its own id, because adding a plaintext loopback redirect to the production client would register it on a client a public website uses.

  • Ports come from the shared dev-app-ports.json, embedded at compile time. The apps’ dev seed and each app’s vite.config.ts read the same file, so a redirect can’t drift off the port its dev server listens on.
  • The redirect is the origin root, except the OHIF viewer’s, whose launch lands on /fhir-viewer, since redirect matching is exact.
  • Scopes mirror each app’s production client, which is what a dev build of the app asks for.
  • It is code, not a migration, because migrations run in release databases too. The function, and its one call in the Tauri host, are compiled only into debug builds.
  • It upserts, so a change to a definition lands on the next boot. They are trusted on first use, like any app the Owner approved.

The debug-only OAuth clients for the first-party apps’ vite dev servers — the authorization server half of wildflowerhealthio_apps::seed_dev_apps.

The first-party SMART apps (Medications, Importer, the OHIF imaging viewer, Strength) ship as rows served from https://wildflowerhealth.io (apps migrations 0005_first_party_apps_to_cloud onward), whose clients register the published-site redirect URI. A debug build also gets an <app>-dev row (wildflowerhealthio_apps::dev_seed) whose launch URL points at the app’s local vite dev server on the port dev-app-ports.json pins, and that row needs its own client, under a random id, whose absolute http://localhost:{port} redirect is what the authorize flow matches (FHIR Sync for Pebble has no row, but its dev server gets a client the same way). They are separate clients rather than extra redirect entries on the production ones because adding a plaintext loopback redirect there would register it on a client that a public website uses.

The redirect path is the origin root for every app but the OHIF viewer, whose launch lands on /fhir-viewer — redirect matching is exact-URL.

Scopes mirror each app’s production client exactly — a dev build of the app requests the same set (apps/*/src/config.ts).

Runtime rather than a migration for the same reason as the app rows: migrations run unconditionally, so a migration-seeded dev client would exist in release databases too. The whole function is #[cfg(debug_assertions)], as is its single call site in the Tauri host.

Upserted (not insert-if-missing) so a definition change lands on the next boot — the same treatment ensure_essential_clients gets, and safe here because nothing but this code owns these rows.
