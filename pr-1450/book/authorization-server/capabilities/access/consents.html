Wildflower, Read in Order

Consents

Covers authorization-server-rust/src/domain/capabilities/access/consents/mod.rs

A consent prompt is a pending request put to whoever may decide it: the Owner, or a paired browser holding enough. There are two surfaces. The authorization-code prompt (/authorization/oauth-consents/{id}) is an app asking, through a browser, for a code. The device page’s prompt (/authorization/devices/{userCode}) is keyed by the code a device or a browser shows: a device request or a browser pairing. Each surface can be read, approved and denied; a code-flow prompt can also be raised for the Owner.

This page holds what the two surfaces share: the three capabilities, the scopes they take, and the shapes the prompt pages read and send. The methods live with their flow, on OAuth Consents and Device Consents.

Approving a request takes its approval scopes: the power to decide it, and to create what approving it creates. Deciding takes wildflower/AuthorizationRequest.u. A code or device approval records a standing grant, so it also takes wildflower/Grant.c. A code approval for an app trusted on first use writes the app’s registration, so it also takes wildflower/Client.c and wildflower/Client.u. A code approval also takes the resource scopes the request asks for: its approver must be able to approve it as asked. Which of these a request takes depends on the request, so the decider checks them on each call, through the DelegatedScopes proof every approval obtains first. The proof also clamps what the Owner ticked to what the approver holds, so an approval is never recorded wider than its approver’s own authority.

Every decision is followed by a republish of the Owner prompt, once the decision has committed: the decided request is no longer waiting, so the host’s popup moves on.

ConsentDecider

Its decisions are approve_oauth_consent, deny_oauth_consent, approve_device_consent and deny_device_consent.

Decide (approve/deny) pending consent prompts — the approve/deny sides of both consent surfaces. Statically gated by AuthorizationRequest.u, and it additionally holds the caller’s own Grant (the approve paths require the request’s approval scopes and reject any delegation beyond the approver’s authority) plus the OwnerApproval port — both lifted from the state. Every decision runs in one write scope, and the OwnerPrompt is republished once it has committed, so the Owner’s popup moves on; a decision that fails rolls back and republishes nothing.

#![allow(unused)]
fn main() {
pub(crate) struct ConsentDecider<S: GrantStore> {
    /// The store every decision reads and writes in one write scope.
    store: S,
    /// The port that republishes the Owner prompt once a decision has
    /// committed.
    owner_approval: Arc<dyn OwnerApproval>,
    /// The approver's own grant: every approval must hold the request's
    /// approval scopes in it, and the Owner's ticks are clamped to it, so an
    /// approval is never recorded wider than its approver's authority.
    approver_grant: Grant,
}
}

decide_and_republish

Every decision on both surfaces runs through here.

Run decide in one write scope and, once it has committed a decision, republish the Owner prompt: the decided request is no longer pending.

#![allow(unused)]
fn main() {
fn decide_and_republish<T>(
    &self,
    decide: impl FnOnce(&mut S::Tx<'_>) -> Result<T, AuthorizationServerError>,
) -> Result<T, AuthorizationServerError> {
    let decided = self.store.write(decide)?;
    self.owner_approval.republish_active();
    Ok(decided)
}
}
