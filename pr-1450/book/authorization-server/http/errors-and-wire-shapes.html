Errors and Wire Shapes

Covers authorization-server-rust/src/http/errors.rs

Covers authorization-server-rust/src/http/wire_representations.rs

These two files are how the server’s answers look on the wire. They render; they decide nothing. The vocabulary of failure is the domain’s AuthorizationServerError, and a handler that gets one back from a capability returns it with ?; this page is where it becomes a status and a body. The same goes for success: the JSON shapes that more than one route sends or reads have one home here, so two surfaces can’t drift apart.

Two rules run through the page. A server-side failure is an opaque 500: the detail goes to the operator’s log, never to the caller. A refused credential is a bare 401 that names, for the host’s request log only, why it was refused.

http::errors

verify_error_response

Both bearer gates answer through it (see verify_request_claims). The tests read the refusal on a response with stamped_refusal.

Map a token-AccessTokenVerifyError to its HTTP response, shared by the auth middlewares. Server-side failures (no keys configured, the key, revocation or browser-session store can’t be read, a configured key’s material is corrupt) are operator problems, so they log and return 500; only a genuinely rejected or revoked token is a 401, stamped with the matching RequestRefusal. Written as an exhaustive match so a new AccessTokenVerifyError variant forces a deliberate status choice rather than silently defaulting to 401.

#![allow(unused)]
fn main() {
pub(crate) fn verify_error_response(context: &str, err: AccessTokenVerifyError) -> Response {
    match err {
        AccessTokenVerifyError::NoSigningKeysConfigured
        | AccessTokenVerifyError::KeyStoreUnavailable(_)
        | AccessTokenVerifyError::RevocationStoreUnavailable(_)
        | AccessTokenVerifyError::BrowserSessionStoreUnavailable(_)
        | AccessTokenVerifyError::SigningKeyUnreadable(_) => internal_error(context, err),
        AccessTokenVerifyError::TokenRejected => unauthorized(RequestRefusal::TokenRejected),
        AccessTokenVerifyError::Revoked => unauthorized(RequestRefusal::Revoked),
    }
}
}

Bare 401 used by the auth middleware when a request lacks a valid bearer token, stamped with refusal (why it lacks one) for the forwarded-request report (see wildflowerhealthio_shared_structures::request_caller).

fn main() {
pub(crate) fn unauthorized(refusal: RequestRefusal) -> Response {
    let mut response = StatusCode::UNAUTHORIZED.into_response();
    response.extensions_mut().insert(refusal);
    response
}
}

AuthorizationServerError

Every /authorization route renders the domain’s failures the same way. Each body carries error, the variant’s name, and one key, the identifier the caller sent. Each “not found” is a 404. Each refusal of an otherwise valid request is a 409 of the same shape. A missing scope, the caller’s or, on an approval, the approver’s, is the shared 403 listing the scopes lacking, from scope-capabilities-rust. An infrastructure failure is the logged, empty 500.

into_response

Render the domain’s failure vocabulary onto the wire, the same way from every /authorization route. Every JSON body carries error, the variant’s name, and one key, the identifier the caller sent:

  • each *NotFound variant is a 404 naming what wasn’t found: id for an OAuth consent, an authorization request or a grant, userCode for a device consent, sid for a browser session, clientId for a client;
  • a refusal of an otherwise valid request is a 409 of the same shape: EssentialClient (clientId), a request to disable a client the Owner needs to get in; RegistrationNotAcknowledged (id), an approval outside the app’s registration without the Owner’s acknowledgement; and LaunchPatientMismatch (id), an approval naming a patient other than the one the app’s launch binds;
  • a missing scope, the caller’s (InsufficientScope) or on an approval the approver’s (InsufficientApproverScope), is the shared 403 listing the scopes lacking;
  • an Infrastructure failure is logged (via the shared InternalError) and answered as an opaque, empty 500.

This is the whole of the HTTP layer’s error knowledge for the /authorization surface; the handlers just ? a Result<_, AuthorizationServerError> from a domain action.

fn into_response(self) -> Response {
    match self {

                error: "OAuthConsentNotFound",
                id,
            }),
        )
            .into_response(),
        AuthorizationServerError::DeviceConsentNotFound { user_code } => (
            StatusCode::NOT_FOUND,
            Json(DeviceConsentNotFoundBody {
                error: "DeviceConsentNotFound",
                user_code,
            }),
        )
            .into_response(),
        AuthorizationServerError::GrantNotFound { id } => (
            StatusCode::NOT_FOUND,
            Json(GrantNotFoundBody {
                error: "GrantNotFound",
                id,
            }),
        )
            .into_response(),
        AuthorizationServerError::BrowserSessionNotFound { sid } => (
            StatusCode::NOT_FOUND,
            Json(BrowserSessionNotFoundBody {
                error: "BrowserSessionNotFound",
                sid,
            }),
        )
            .into_response(),
        AuthorizationServerError::ClientNotFound { client_id } => (
            StatusCode::NOT_FOUND,
            Json(ClientNotFoundBody {
                error: "ClientNotFound",

            }),
        )
            .into_response(),
        AuthorizationServerError::EssentialClient { client_id } => (
            StatusCode::CONFLICT,
            Json(EssentialClientBody {
                error: "EssentialClient",
                client_id,
            }),
        )
            .into_response(),
        AuthorizationServerError::AuthorizationRequestNotFound { id } => (
            StatusCode::NOT_FOUND,
            Json(AuthorizationRequestNotFoundBody {
                error: "AuthorizationRequestNotFound",
                id,
            }),
        )
            .into_response(),
        AuthorizationServerError::RegistrationNotAcknowledged { id } => (
            StatusCode::CONFLICT,
            Json(RegistrationNotAcknowledgedBody {
                error: "RegistrationNotAcknowledged",
                id,
            }),
        )
            .into_response(),
        AuthorizationServerError::LaunchPatientMismatch { id } => (
            StatusCode::CONFLICT,
            Json(LaunchPatientMismatchBody {
                error: "LaunchPatientMismatch",
                id,
            }),
        )
            .into_response(),
        AuthorizationServerError::InsufficientScope { missing_scopes } => {
            insufficient_scope(missing_scopes)
        }
        AuthorizationServerError::InsufficientApproverScope {
            approver_missing_scopes,
        } => insufficient_scope(approver_missing_scopes),

            InternalError::new(context, source).into_response()

CacheSuppressed

OAuth requires it of every token response, success or error, and the server applies it more widely. Making it a wrapper makes it part of the value rather than a step a handler can forget; cache_suppress applies it as one layer to all of /authorization.

Wrapper that stamps the RFC 6749 §5.1/§5.2 cache-suppression headers (Cache-Control: no-store, Pragma: no-cache) onto the wrapped response. Token- and device-authorization-endpoint responses — success or error — must never be cached; wrapping makes that part of the value instead of a step a call site can forget. The same wrapper renders the authorize-status poll (its Approved redirect carries a redeemable code), the start limit’s 429, sign-out and, applied as a blanket layer, every Owner /authorization/* response. The headers are inserted, not appended, so nothing ends up with either twice.

Result the approving surface sees after approving or denying a consent prompt: {"status":"approved"} or {"status":"denied"}, with a redirect for a code-flow decision.

A code-flow decision carries the client callback URL (code + state, or error=access_denied + state, appended to the client’s redirect_uri) so the approving surface can complete the flow directly when it is the requesting browser (the consent card) — no separate poll of /oauth/authorize/{id} needed. Device-flow decisions have no client redirect_uri, so redirect is None and (thanks to skip_serializing_if) omitted from the wire entirely.

pub(crate) enum ConsentResult {
    /// The request was approved: a code-flow request's code is issued, a
    /// device's grant stands, a pairing's browser may now sign in.
    Approved {
        /// The app's callback carrying the code and the app's `state`, for
        /// the consent card to leave for; absent for a device-page decision,
        /// whose device or browser polls for its result.
        redirect: Option<String>,
    },
    /// The request was denied: declined, or an approval that granted
    /// nothing. A code-flow approval is a deny too when the requesting
    /// browser's session has ended or the app was disabled since.
    Denied {
        /// The app's callback carrying `error=access_denied` and the app's
        /// `state`; absent for a device-page decision.
        redirect: Option<String>,
    },
}
}
