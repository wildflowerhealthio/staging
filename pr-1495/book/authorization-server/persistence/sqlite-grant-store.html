SQLite Grant Store

Covers authorization-server-rust/src/db/grant_store.rs

SqliteGrantStore is the Grant Store port’s SQLite adapter. It holds a pool of connections onto the host’s shared database file, applies this crate’s migrations when it is opened, and opens the port’s two scopes on a connection it checks out of the pool: a read scope in autocommit, where each statement sees a committed state and no lock is held between statements, and a write scope inside BEGIN IMMEDIATE, which takes the write lock before its first read.

SQLite admits one writer at a time across every connection to the file. A second write scope’s BEGIN IMMEDIATE waits for the first to commit, for up to the connection’s busy timeout, and then fails. That is what lets a capability read a row, decide, and write it back in one write scope without another writer landing in between.

The revocation store and lock order

The host’s token revocation store, which holds the per-token denylist and each app’s revocation epoch, is not in this adapter. It reads and writes through the host’s shared rusqlite connection: another connection onto the same file, behind a lock of its own. No write scope touches the revocation store. Taking that connection’s lock while holding the file’s write lock risks a lock-order stall: the other connection, mid-write, can be waiting for the write lock this scope holds, and the two wait on each other until the busy timeout. So a capability reads or writes the revocation store before or after its write scope, never inside it, which is why two operations open two scopes.

#![allow(unused)]
fn main() {
fn write<T, E: From<AuthorizationServerError>>(
    &self,
    f: impl FnOnce(&mut Self::Tx<'_>) -> Result<T, E>,
) -> Result<T, E> {
    let mut conn = self.connection()?;
    let sqlite: &mut SqliteConnection = &mut conn;
    sqlite
        .immediate_transaction(|conn| {
            f(&mut SqliteGrantTx { conn }).map_err(ScopeError::Closure)
        })
        .map_err(|error| match error {
            ScopeError::Closure(error) => error,
            ScopeError::Transaction(error) => {
                E::from(AuthorizationServerError::infrastructure(
                    "grant store transaction failed",
                    error,
                ))
            }
        })
}
}

MIGRATIONS

A migration runs once per database, so a shipped migration is never edited. An install that already ran it never reads it again; a change lands as a new migration, which reaches fresh and upgraded installs alike. The tests hold each migration to that: each drives a database to the version just before it with MigrationsThrough, plants the rows an install could hold, upgrades, and checks the result, often reverting the migration too, to show its down.sql restores what was there.

The authorization server migrations, embedded from the crate’s migrations/ tree at compile time (diesel layout: <version>_<name>/up.sql + down.sql). Applied once per database in SqliteGrantStore::new via wildflowerhealthio_persistence::run_diesel_migrations under MIGRATION_NAMESPACE (see that runner for why the stock diesel harness can’t be shared across slices). Each migration’s header says what it changes and why (see migrations/); because each runs only once per database, an upgrade neither re-drops nor re-seeds.
