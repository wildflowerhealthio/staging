A few things the domain must do reach outside the store: telling the host a request now waits for the Owner, revoking and checking tokens in the revocation store the FHIR server shares, and asking the host whether a visitor may start another request. The domain doesn’t learn what does these. It calls out through a port, a small trait it owns; an adapter implements the port on the concrete runtime type. The capabilities hold the ports as trait objects lifted from the state, and their unit tests wire in fakes that record the calls or fail on purpose.

The ports live in ports/, bare contracts. Two of the adapters live in adapters/; the start gate’s real adapter is the host’s, since the host is who decides.

ports

Host/HTTP-seam dependency-inversion traits the authorization server’s domain capabilities call out through — so domain::capabilities can trigger the runtime side-effects a consent or logout flow needs without the domain learning axum, the Owner prompt’s watch channel, or the revocation store’s concrete type. The real implementations live in crate::adapters, on AuthorizationServerState; tests wire in-memory fakes. Mirrors apps-rust’s ports/.

  • OwnerApproval — ask the Owner: republish the OwnerPrompt to the host after any transition that may change it (see the trait);
  • Revocation / RevocationCheck — denylist a token jti or bulk-revoke a subject, and answer whether a token is revoked; the seams the revoking capabilities, logout, and the token verifier go through;
  • AuthorizationStartGate — the host’s say over whether a request may start an authorization request, which the limit on /oauth/authorize and /oauth/device_authorization asks. Public: the host implements it.

adapters

The composition layer: the crate::ports seams implemented onto the concrete runtime types. Each adapter lives here rather than beside its trait so ports/ stays a set of bare contracts the domain can name without learning what implements them.

ports::owner_approval

OwnerApproval — asking the Owner: the seam a pending-consent transition calls to republish the request awaiting the Owner’s approval after it changes which requests are pending.

OwnerApproval

Tell the host which request now waits for the Owner. Any transition that may change the Owner prompt calls this after its write: a new /oauth/authorize, /oauth/device_authorization or pairing request, a request raised for the Owner, an approval or a denial. So the host notifies about a new request, and its server page shows the one waiting.

Republish the OwnerPrompt, the newest request awaiting the Owner, to the host.

Any transition that may change which pending request is newest — a fresh /oauth/device_authorization or /oauth/authorize insert, a browser pairing’s start or rename, a prompt raised for the Owner, an approve or a deny on either consent surface — calls this after the store write, so the host notifies a new request and its server page shows the one pending. The real implementation (in crate::adapters, on AuthorizationServerState) recomputes the Owner prompt from the store and publishes it on its watch channel; a test fake just records that it was asked to.

The adapter

The Owner prompt’s republish seam (crate::ports) adapted onto the bare AuthorizationServerState. See the module docs for the composition layer.

The adapter is the shared state itself, so an Arc<AuthorizationServerState> is the port handle the capabilities hold.

Recompute the OwnerPrompt from the store and publish it on its watch sender. Call after every transition that may change it (see OwnerApproval).

The DB read happens inside send_if_modified, so the watch sender’s internal lock serialises the read+publish pair across concurrent callers: whichever caller commits last to SQLite is also whichever publishes last to the watch (and the published value matches what is in the DB at that moment). Without this, a thread that read the newest request before a concurrent thread’s commit could overwrite the watch with a stale one after the concurrent publish — the host would advertise a request whose row was already handled.

Uses send_if_modified so a transition that leaves the newest request unchanged (e.g. denying an older one) does not produce a spurious change of the server’s status.

On a DB-read failure the watch keeps what it holds: None there says nothing is pending, which the host takes to mean every request it notified for is settled, so a transient failure publishing it would re-notify each one still waiting. A request handled meanwhile drops off on the next mutation or reaper tick that reads.

Either way it then pings pending_consents_recomputed_tx, so a PendingConsentWatcher rereads its request: one decided or expired while a newer one stays newest changes nothing on the watch above.

#![allow(unused)]
fn main() {
fn republish_active(&self) {
    self.owner_approval_tx.send_if_modified(|current| {
        let next = match self.store.read(|tx| tx.owner_prompt(Utc::now())) {
            Ok(next) => next,
            Err(error) => {
                tracing::warn!("owner_prompt query failed; keeping the last: {error}");
                return false;
            }
        };
        if *current == next {
            false
        } else {
            *current = next;
            true
        }
    });
    self.pending_consents_recomputed_tx.send_replace(());
}
}

  • The read happens inside send_if_modified, under the channel’s lock, so whichever caller commits last to SQLite also publishes last, and the channel never goes back to a request already handled.
  • A publish that changes nothing is suppressed, so denying an older request leaves the server’s status alone.
  • A failed read keeps what the channel holds. Publishing nothing would tell the host every request it notified is settled, and a passing failure would then re-notify each one still waiting. A request handled meanwhile drops off at the next write or reaper tick.
  • Either way it pings the recompute channel, so a PendingConsentWatcher rereads its request: one decided under a newer request changes nothing on the published channel.

The OAuth Endpoints tests hold it to clearing the prompt once a consent is decided.

ports::revocation

Revocation — the token-revocation seam the domain calls out through, so the scope-gated capabilities (GrantsRevoker, TokenRevoker) and the logout session-revoke stay testable against a stub instead of the concrete RevocationStore. Object-safe on purpose: the capabilities hold an Arc<dyn Revocation> lifted from the state.

Revocation

Revoke issued tokens: denylist one token’s jti until its expiry, tagged with why, or move a subject’s revocation epoch to now, which kills every access and refresh token issued to it before. A grant’s revoke, /authorization/revocations, logout and an app revoking its own token at /oauth/revoke go through it. Errors are strings, so the port doesn’t carry the store’s error type.

Revoke issued tokens. Both operations are implemented over the shared RevocationStore; a test fake records the calls (or fails, to prove a caller swallows or surfaces the error). Errors are stringified so the port stays free of the store’s concrete error type.

#![allow(unused)]
fn main() {
pub(crate) trait Revocation: Send + Sync + 'static {
    /// Denylist a single token by its `jti` until `expires_at` (after which
    /// expiry validation rejects it regardless), tagging the row with `reason`.
    ///
    /// # Errors
    ///
    /// Returns the store failure (stringified) when the write fails.
    fn revoke_jti(&self, jti: &str, expires_at: DateTime<Utc>, reason: &str) -> Result<(), String>;

    /// Bump a subject's revocation epoch to now, killing every access **and**
    /// refresh token issued to it before this instant — the bulk revoke behind a
    /// grant revoke and `/authorization/revocations` subject revoke.
    ///
    /// # Errors
    ///
    /// Returns the store failure (stringified) when the write fails.
    fn revoke_subject_as_of_now(&self, subject: &str) -> Result<(), String>;
}
}

RevocationCheck

Ask whether a token is revoked: by its jti on the denylist, or by being issued to its subject before the subject’s epoch. A missing jti skips the first check, a missing issue time the second. The token verifier asks it behind every gate, and so, in-process, the FHIR server’s; refresh redemption asks whether a family began before its app’s epoch. Every caller fails closed on an error.

Answer whether an issued token has been revoked — the read side of the same store, kept as its own object-safe seam so the token verifier can be tested against a stub. Errors are stringified for the same reason as Revocation’s.

The token verifier runs the full check here (the per-jti denylist and the per-subject epoch), behind the authorization server’s gates and, through InProcessTokenVerifier, HFS’s bearer auth. Refresh redemption asks it whether a family began before its client’s epoch. Both fail closed on a store error.

#![allow(unused)]
fn main() {
pub(crate) trait RevocationCheck: Send + Sync + 'static {
    /// Whether the token identified by `jti` (denylisted individually) or
    /// issued to `subject` at `issued_at` (before the subject's revocation
    /// epoch) is revoked. A missing `jti` skips the per-token check; a missing
    /// `issued_at` skips the epoch check.
    ///
    /// # Errors
    ///
    /// Returns the store failure (stringified) when the read fails; the caller
    /// fails closed.
    fn is_revoked(
        &self,
        jti: Option<&str>,
        issued_at: Option<DateTime<Utc>>,
        subject: &str,
    ) -> Result<bool, String>;
}
}

ports::authorization_start_gate

AuthorizationStartGate — the host’s say over how fast authorization requests are started, asked by the limit on the two routes that start one (http::middleware::authorization_start_limit).

AuthorizationStartGate

The host’s say over how fast authorization requests start. /oauth/authorize and /oauth/device_authorization park requests the Owner is asked about, and a stranger shouldn’t be able to raise them without end. The server knows nothing of who is asking beyond the request; the host’s listener puts what it knows of the connection in the request’s extensions, and the host decides from those. A request it admits has spent from whatever allowance it keeps; one it refuses is answered 429 Too Many Requests.

Whether a request may start an authorization request (GET /oauth/authorize, POST /oauth/device_authorization), handed to crate::setup_authorization_server.

The authorization server knows nothing of who is asking beyond the request; the host, whose listener put what it knows of the connection in the request’s extensions (its connect info), decides. Asked at most once per request: before the request is parsed, or, for a request carrying a browser session that can decide consents or an /oauth/authorize request carrying no browser session, only once the request is to be raised for the Owner. POST /authorization/oauth-consents/{id}/ask-owner, which raises a parked request for the Owner, asks it too, only when it raises one. A request it admits has spent from whatever allowance it keeps, and one it refuses is answered 429 Too Many Requests.

fn main() {
pub trait AuthorizationStartGate: Send + Sync + 'static {
    /// Whether to admit the request `request_extensions` belong to, spending
    /// from its allowance when it does.
    fn admit(&self, request_extensions: &Extensions) -> bool;
}
}
