Setup

Covers authorization-server-rust/src/lib.rs

Covers authorization-server-rust/src/config.rs

The authorization server isn’t a process of its own. It is one slice of the Wildflower host, and the host builds it once, at boot, with one call: setup_authorization_server. The host hands over what only it has: the shared database, the shared revocation store, its configuration, a channel to hear about the Owner prompt on, and its say over how fast requests may start. It gets back a router to merge, the shared state its own gates need, and four in-process handles.

This page is that seam: the configuration, the constants that name the server’s own clients and the Owner’s authority, the call itself, the background sweeps it starts, and what the crate root re-exports for the host.

The Wildflower authorization server: the OAuth 2.0 and SMART App Launch authorization server in front of the Owner’s FHIR server. It decides which apps, devices and browsers may reach the Owner’s data, asks the Owner when it must, and signs the access tokens the FHIR server checks.

setup_authorization_server

Build the server over the host’s database, and start it working. In order:

  1. Open and seed the store (open_and_seed_store): run the migrations, make sure a signing key is active, and rewrite the server’s own clients.
  2. Build the shared state (AuthorizationServerState) from the config, with a stale-session cutoff at the run’s start. The host ends an Owner session once the server’s last launch view closes, so one no open view holds is one whose ending was missed, as across the app’s exit, or failed. The run’s start cuts off the Owner sessions earlier runs signed in, except those the host’s launch views still open hold: setup is handed those views’ sign-in codes, whichever run minted them, and exempts the sessions they signed in, so the restart a return from a suspend brings on iOS keeps an open view signed in. The others are stale, and nothing is written for them, so a store that can’t be written then doesn’t keep the server from starting. Paired sessions stand.
  3. Publish the Owner prompt on owner_approval_tx. The channel’s value doesn’t survive a restart, but the row does, so a request left pending across a restart is in the server’s first status, and the host notifies about it.
  4. Start the background sweeps below.
  5. Build the router, whose routes are at /.well-known/jwks.json, /oauth/* and /authorization/*. The host merges it as it is.
  6. Build the in-process handles the host keeps.

The host builds revocation_store once and passes the same store to the FHIR server’s adapter, so the authorization server’s gates and the FHIR server read one denylist. Where no visitor can reach the server, the host passes AdmitEveryAuthorizationStart as the start gate.

Build the authorization-server-rust HTTP surface over the host-owned diesel connection pool (the same app-wide wildflowerhealthio_persistence::open_pool pool the other diesel-backed slices ride). Runs idempotent bootstrap (schema migrations, signing-key seed, essential-client seed), and:

  • publishes the OwnerPrompt, the newest request awaiting the Owner (device-code and authorization-code requests and browser pairings alike), on owner_approval_tx. On the Tauri host, the server’s run reports it as its detail, which the base’s server status carries and from which the host notifies each new request. Seeding at boot means a request that was pending across an app restart is still reported (the row survived in SQLite, the in-memory watch value didn’t);
  • cuts off, at the run’s start, the same-device sessions earlier runs signed in, except those open_views_sign_in_codes signed in: the codes of the host’s launch views still open, whichever run minted them. The host ends a same-device session once the last of the server’s launch views has closed, so a session no open view holds is one whose ending was missed, as across the app’s exit, or failed. So the StaleSessionCutoff invalidates sessions before the run’s start, with the open views’ sessions exempt: it makes the others stale, writing nothing, so a store that can’t be written doesn’t keep the server from starting, and the browser is sent through sign-in again, which the host’s next launch does. Paired sessions stand;
  • returns a Router whose routes are at /.well-known/jwks.json, /oauth/*, and /authorization/* (authenticated bearer JWT + per-resource scope gates via the Scoped<…> extractors) — the slice owns its mount paths so the caller just .merge()s;
  • returns the Arc<AuthorizationServerState> the caller passes to authorization_server_auth_middleware to gate fhir-r4-rust;
  • returns the LaunchContextMinter an in-process launcher mints each SMART App Launch launch value through, which /oauth/authorize then consumes;
  • returns the SameDeviceSignInCodeMinter the host mints each same-device sign-in code through, which /oauth/sign-in then redeems, and which ends the sessions codes signed in when the host asks;
  • returns the PendingConsentWatcher the host waits on for a pending consent it opened to be decided or expire;
  • returns the InProcessTokenVerifier the host’s FHIR server verifies each bearer through, in-process.

authorization_start_gate says whether a request may start an authorization request (GET /oauth/authorize, POST /oauth/device_authorization): asked for every one that carries no live browser session, which is answered 429 when it refuses. Pass AdmitEveryAuthorizationStart where no visitor reaches the server.

Every token this server mints carries the server’s origin (AuthorizationServerConfig::server_origin) as both iss and aud, and the bearer gates accept no other. See docs/Origins/Explanation.md.

revocation_store is the shared token-revocation store the host builds once on the shared database and threads into both this setup and fhir-r4-rust’s HFS adapter, so the auth gate and the FHIR server read one denylist/epoch store.

Errors

Returns an error if opening and seeding the store fails.

#![allow(unused)]
fn main() {
pub fn setup_authorization_server(
    pool: DieselPool,
    revocation_store: RevocationStore,
    config: &AuthorizationServerConfig,
    owner_approval_tx: watch::Sender<Option<OwnerPrompt>>,
    authorization_start_gate: Arc<dyn AuthorizationStartGate>,
    open_views_sign_in_codes: &[SameDeviceSignInCode],
) -> anyhow::Result<AuthorizationServer> {
    let store = seeding::open_and_seed_store(
        pool,
        &config.host_app_client_scopes,
        &config.fhir_ui_client_id,
        &config.server_origin,
    )?;
    let server_origin: Arc<str> =
        wildflowerhealthio_shared_structures::origin_string(&config.server_origin).into();
    let same_device_sign_in_codes = Arc::new(SameDeviceSignInCodes::new());
    let stale_session_cutoff = Arc::new(StaleSessionCutoff::new(
        Utc::now(),
        open_views_sign_in_codes
            .iter()
            .filter_map(SameDeviceSignInCode::signed_in_sid)
            .collect(),
    ));
    let (pending_consents_recomputed_tx, pending_consents_recomputed_rx) = watch::channel(());
    let state = Arc::new(AuthorizationServerState {
        store: store.clone(),
        revocation_store: revocation_store.clone(),
        server_origin: server_origin.clone(),
        device_page: Arc::new(http::device_page_url(&config.server_origin)),
        launcher_base: config.launcher_base.clone(),
        owner_approval_tx,
        pending_consents_recomputed_tx,
        owner_grant: Grant::new(OWNER_SCOPES.to_vec()),
        same_device_sign_in_codes: same_device_sign_in_codes.clone(),
        sign_in_destinations: Arc::new(SignInDestinations::new(
            config.server_origin.clone(),
            config.launcher_base.clone(),
            config.authorization_app_base.clone(),
            config.launcher_url.clone(),
            config.authorization_url.clone(),
        )),
        authorization_start_gate,
        last_seen_throttle: Arc::new(LastSeenThrottle::new()),
        stale_session_cutoff,
    });
    // Publish the Owner prompt from SQLite so a request that was
    // pending across an app restart is reported in the run's first detail —
    // the `watch` value itself doesn't survive the process, but the row
    // does.
    ports::OwnerApproval::republish_active(state.as_ref());
    spawn_device_consent_reaper(state.clone());
    // Reclaim the authorization server rows past their retention window: once at startup, then
    // daily.
    spawn_retention_sweep(store);
    // Reclaim expired denylist rows: once at startup, then daily.
    spawn_revocation_purge(revocation_store);
    let router = http::router(state.clone());
    let launch_context_minter = LaunchContextMinter::new(state.store.clone());
    let in_process_token_verifier = InProcessTokenVerifier::new(&state);
    let same_device_sign_in_code_minter =
        SameDeviceSignInCodeMinter::new(same_device_sign_in_codes, state.store.clone());
    let pending_consent_watcher =
        PendingConsentWatcher::new(state.store.clone(), pending_consents_recomputed_rx);
    Ok(AuthorizationServer {
        router,
        state,
        launch_context_minter,
        same_device_sign_in_code_minter,
        pending_consent_watcher,
        in_process_token_verifier,
    })
}
}

The background sweeps

setup_authorization_server starts three loops on the runtime. None changes what the server honours: each either reclaims rows the read paths already refuse, or republishes what the store already says. After a long pause such as a suspend, each runs once rather than catching up on the ticks it missed.

The reaper republishes the Owner prompt, because republishing otherwise happens only after a write, and an idle server would go on advertising a request that has expired.

How often the background reaper recomputes the OwnerPrompt, so the watch channel drops a request whose expires_at has passed without any HTTP mutation arriving to trigger a republish. Picked well under the 5-minute DEVICE_AUTHORIZATION_TTL so a freshly-expired request clears within seconds; the recompute is two LIMIT 1 reads, one per request table, and the watch sender suppresses no-op publishes.

Spawn the background reaper that periodically recomputes the OwnerPrompt. Mutation-driven republishing alone leaves the watch advertising a request whose row has expired in the meantime — without this task, an idle host stays stuck on the now-expired request until some unrelated handler happens to write. The reaper drops the stale request within DEVICE_CONSENT_REAPER_INTERVAL, and send_if_modified suppresses ticks that leave it unchanged so an idle server publishes nothing.

#![allow(unused)]
fn main() {
fn spawn_device_consent_reaper(state: Arc<AuthorizationServerState>) {
    tokio::spawn(async move {
        let mut ticks = interval(DEVICE_CONSENT_REAPER_INTERVAL);
        // A long pause (suspend/resume, debugger break) must not cause a
        // burst of catch-up republishes — one tick after the gap is the
        // right behaviour.
        ticks.set_missed_tick_behavior(MissedTickBehavior::Delay);
        // The first tick fires immediately; the boot-time republish in
        // `setup_authorization_server` already covered that, so consume it before
        // the loop.
        ticks.tick().await;
        loop {
            ticks.tick().await;
            ports::OwnerApproval::republish_active(state.as_ref());
        }
    });
}
}

Spawn the background sweep that deletes the authorization server rows past their retention window — once at startup (the interval’s immediate first tick), then every RETENTION_SWEEP_INTERVAL. The windows and their rationale live in domain::retention.

Space reclamation only: every row it touches is already past expires_at (or, for a browser session, its revoked_at) and rejected by the read paths, so nothing here changes what the server honours. A failed sweep is logged and retried next tick.

Runs on spawn_blocking rather than a runtime worker: pool.get() alone can park for r2d2’s 30s connection timeout, and the sweep then holds one write transaction across a delete per table.

#![allow(unused)]
fn main() {
fn spawn_retention_sweep(store: SqliteGrantStore) {
    tokio::spawn(async move {
        let mut ticks = interval(RETENTION_SWEEP_INTERVAL);
        // A long pause (suspend/resume) must not queue up catch-up sweeps —
        // one tick after the gap reclaims the same rows anyway.
        ticks.set_missed_tick_behavior(MissedTickBehavior::Delay);
        loop {
            // First tick is immediate → startup sweep; then daily.
            ticks.tick().await;
            // Cheap clone (the pool is an `Arc` inside) so the loop keeps its own
            // handle for the next tick.
            let sweep_store = store.clone();
            let swept = tokio::task::spawn_blocking(move || {
                domain::retention::purge_expired(&sweep_store, Utc::now())
            })
            .await;
            match swept {
                Ok(Ok(purged)) if !purged.is_empty() => tracing::info!(
                    refresh_token_families = purged.refresh_token_families,
                    code_authorization_requests = purged.code_authorization_requests,
                    user_code_requests = purged.user_code_requests,
                    authorization_codes = purged.authorization_codes,
                    browser_sessions = purged.browser_sessions,
                    "swept the authorization server rows past their retention window",
                ),
                Ok(Ok(_)) => {}
                Ok(Err(error)) => {
                    tracing::warn!(%error, "the authorization server retention sweep failed")
                }
                Err(error) => {
                    tracing::warn!(%error, "the authorization server retention sweep task failed")
                }
            }
        }
    });
}
}

Spawn the background sweep that purges expired rows from the revocation denylist — once at startup (the interval’s immediate first tick) then every REVOCATION_PURGE_INTERVAL. Purely space reclamation: an expired jti is already rejected by expiry validation, denylisted or not.

#![allow(unused)]
fn main() {
fn spawn_revocation_purge(revocation_store: RevocationStore) {
    tokio::spawn(async move {
        let mut ticks = interval(REVOCATION_PURGE_INTERVAL);
        ticks.set_missed_tick_behavior(MissedTickBehavior::Delay);
        loop {
            // First tick is immediate → startup purge; then daily.
            ticks.tick().await;
            // Retention floor = the longest access token we mint (a browser
            // session's token lives as long as the session, at most a day,
            // past the 15-min OAuth `ACCESS_TOKEN_TTL`), so a denylist row is
            // never dropped while its token could still be live — even if the
            // `/authorization/revocations` caller supplied a too-early
            // `expiresAt`. See `RevocationStore::purge_expired`.
            match revocation_store.purge_expired(Utc::now(), LONGEST_BROWSER_SESSION_TTL) {
                Ok(purged) if purged > 0 => {
                    tracing::info!(purged, "swept expired revoked jtis");
                }
                Ok(_) => {}
                Err(error) => tracing::warn!(%error, "revoked-jti sweep failed"),
            }
        }
    });
}
}
