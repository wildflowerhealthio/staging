Token Verifier

Covers authorization-server-rust/src/domain/capabilities/session/token_verifier.rs

The token verifier answers one question for every request that presents an access token: is this a live token this server minted for itself? It is the single place that question is answered, so a token is accepted or refused the same way wherever it is presented.

Its answer is the token’s VerifiedClaims, or an AccessTokenVerifyError saying why not. Revocation comes last: a token is first proven genuine by verify_access_token against the stored keys, and only then asked whether it has since been withdrawn: by its browser session, in the grant store, and by its jti or its subject’s epoch, in the host’s revocation store. A logout denylists a jti; an Owner’s revoke or a grant’s revoke moves a subject’s epoch; signing a browser out revokes its session. A browser session’s own token, the one its cookie holds, lasts only as long as the session: the host ends the Owner’s same-device session by expiring it, before its token would expire, and the verifier refuses the token from then on. It refuses the token of a same-device session the stale-session cutoff makes stale the same way. The tokens apps were issued under the session don’t end with its expiry, only with its revocation.

The tests verify against a fake store with one signing key, and a recording revocation check.

Verify presented access tokens. Generic over the store port so it’s unit-testable against the fake; the binding instantiates it over the concrete SqliteGrantStore.

#![allow(unused)]
fn main() {
pub(crate) struct TokenVerifier<S: GrantStore> {
    /// The grant store, holding the signing keys a token must be signed with
    /// and the browser sessions a token's `sid` may name.
    store: S,
    /// The host's revocation check: the per-`jti` denylist and the per-subject
    /// epoch, kept outside the grant store.
    revocation: Arc<dyn RevocationCheck>,
    /// The server's bare origin: the one `iss` and the one `aud` accepted, so
    /// a token another server minted is refused by these alone.
    server_origin: Arc<str>,
    /// The cutoff before which a same-device session is stale: a browser
    /// session's own token needs its session live under it.
    stale_session_cutoff: Arc<StaleSessionCutoff>,
}
}

verify

Verify token: its iss and aud must both be this server’s origin, so a token another server minted is refused by construction. See docs/Origins/Explanation.md.

Revocation is the last gate: the token is cryptographically valid, but a logout / owner revoke / grant revoke may have denylisted its jti or bumped the subject’s epoch since it was minted, or revoked the browser session its sid names. A sid that names no session row reads as revoked, so a token naming a session the server never had is refused too. A browser session’s own token is also refused once the session is no longer live, which can be before the token expires. Both authN gates, the browser-session cookie checks, and through InProcessTokenVerifier the FHIR server, funnel through here, so it runs the complete check (per-jti denylist, per-subject epoch and browser session). A token with no sid has no session to check. Every store failure fails closed, never admitting the token, and the gates answer it with a 500, not a 401.

Errors

AccessTokenVerifyError::TokenRejected for a bad, expired, wrong-issuer or wrong-audience token, or a browser session’s own token once the session is no longer live; AccessTokenVerifyError::Revoked for a revoked one; the server-side variants when the key, revocation or browser-session store can’t be read.

#![allow(unused)]
fn main() {
pub(crate) fn verify(&self, token: &str) -> Result<VerifiedClaims, AccessTokenVerifyError> {
    // A connection that can't be checked out at all fails like the key
    // read that is the scope's first statement.
    let claims = self
        .store
        .read(|tx| Ok(self.verify_signed_and_session_live(tx, token)))
        .map_err(AccessTokenVerifyError::KeyStoreUnavailable)??;
    let revoked = self
        .revocation
        .is_revoked(claims.jti.as_deref(), claims.issued_at, &claims.subject)
        .map_err(AccessTokenVerifyError::RevocationStoreUnavailable)?;
    if revoked {
        return Err(AccessTokenVerifyError::Revoked);
    }
    Ok(claims)
}
}

fn main() {
fn revocation_is_the_last_gate_and_fails_closed() {
    let (store, key) = store_with_key();
    let token = mint(&key, ORIGIN, ORIGIN);
    let jti = verify_access_token(
        &token,
        &store.tx().all_signing_keys().unwrap(),
        &AccessTokenVerifyOptions {
            expected_issuer: ORIGIN,
            accepted_audiences: &[ORIGIN.to_owned()],
        },
    )
    .unwrap()
    .jti
    .expect("minted tokens carry a jti");

    let revoked = TokenVerifier::new(
        FakeGrantStore::default(),
        Arc::new(FakeRevocation {
            revoked_jtis: vec![jti],
            ..FakeRevocation::default()
        }),
        ORIGIN.into(),
        Arc::new(StaleSessionCutoff::none()),
    );
    // Re-seed the key so the revoked verifier can check the signature.
    revoked.store.tx().insert_signing_key(&key).unwrap();
    assert!(matches!(
        revoked.verify(&token),
        Err(AccessTokenVerifyError::Revoked)
    ));

    let failing = TokenVerifier::new(
        store,
        Arc::new(FakeRevocation {
            fail: true,
            ..FakeRevocation::default()
        }),
        ORIGIN.into(),
        Arc::new(StaleSessionCutoff::none()),
    );
    assert!(matches!(
        failing.verify(&token),
        Err(AccessTokenVerifyError::RevocationStoreUnavailable(_))
    ));
}
}

verify_signed_and_session_live

Verify token’s signature, iss and aud against the keys in tx, and refuse it when the browser session its sid names is revoked or has no row, or, for the session’s own token, is no longer live.

#![allow(unused)]
fn main() {
fn verify_signed_and_session_live(
    &self,
    tx: &mut (impl SigningKeysTx + BrowserSessionsTx),
    token: &str,
) -> Result<VerifiedClaims, AccessTokenVerifyError> {
    let keys = tx
        .all_signing_keys()
        .map_err(AccessTokenVerifyError::KeyStoreUnavailable)?;
    let claims = verify_access_token(
        token,
        &keys,
        &AccessTokenVerifyOptions {
            expected_issuer: &self.server_origin,
            accepted_audiences: &[self.server_origin.to_string()],
        },
    )?;
    if let Some(sid) = claims.sid.as_deref() {
        if claims.subject == BROWSER_SESSION_CLIENT_ID {
            ensure_own_session_live(tx, sid, &self.stale_session_cutoff, Utc::now())?;
        } else if tx
            .is_browser_session_revoked(sid)
            .map_err(AccessTokenVerifyError::BrowserSessionStoreUnavailable)?
        {
            return Err(AccessTokenVerifyError::Revoked);
        }
    }
    Ok(claims)
}
}

ensure_own_session_live

Refuse a browser session’s own token, the one its cookie holds, once the session sid is no longer live at now under stale_session_cutoff: Revoked when the session is revoked or has no row, TokenRejected when it is otherwise not live. A session can end before its token does: the host ends a same-device session by expiring it, and the cutoff makes one stale. The tokens apps were issued under the session outlive its ending, and only its revocation ends them.

#![allow(unused)]
fn main() {
fn ensure_own_session_live(
    tx: &mut impl BrowserSessionsTx,
    sid: &str,
    stale_session_cutoff: &StaleSessionCutoff,
    now: DateTime<Utc>,
) -> Result<(), AccessTokenVerifyError> {
    let session = tx
        .browser_session_by_sid(sid)
        .map_err(AccessTokenVerifyError::BrowserSessionStoreUnavailable)?;
    match session {
        None => Err(AccessTokenVerifyError::Revoked),
        Some(session) if session.revoked_at.is_some() => Err(AccessTokenVerifyError::Revoked),
        Some(session) if !session.is_live_at(now, stale_session_cutoff) => {
            Err(AccessTokenVerifyError::TokenRejected)
        }
        Some(_) => Ok(()),
    }
}
}
