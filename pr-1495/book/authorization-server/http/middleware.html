The middleware are the gates a request passes before a handler sees it. Each enforces one rule:

  • Only a live token of this server’s gets past a bearer gate. Two gates check it, the session gate on /authorization and the bearer gate the host layers over its own routes, and both run one pipeline, so they can’t disagree about a token.
  • Starting requests that may reach the Owner is rate-limited. Anyone who knows the server’s domain can start an authorization request, and each one raised for the Owner pops up on the Owner’s device. The start limit asks the host whether to admit each one.
  • Nothing on /authorization is cached. Every response there is privileged.

Middleware verify tokens only through the token verifier, never against a store; the source guard middleware_verifies_only_through_the_token_verifier holds that. The Request Caller, Authorization Start Limit and Cache Suppression integration tests hold these gates end to end.

http::middleware::require_auth

try_bearer_token_from_headers

Extract the access token from the request’s Authorization: Bearer header — the only credential the server accepts. The scheme match is case-insensitive; None when the header is absent, not UTF-8, or another scheme. The returned slice borrows the header, so a request pays no per-request JWT copy on the way to verification.

#![allow(unused)]
fn main() {
pub fn try_bearer_token_from_headers(headers: &HeaderMap) -> Option<&str> {
    let value = headers.get(header::AUTHORIZATION)?.to_str().ok()?;
    let prefix = "bearer ";
    // Case-insensitive prefix check against just the scheme bytes — avoids
    // lowercasing (and reallocating) the whole header, which carries the
    // full JWT. The returned slice borrows the header, so no copy is made.
    if !value
        .get(..prefix.len())
        .is_some_and(|p| p.eq_ignore_ascii_case(prefix))
    {
        return None;
    }
    Some(value[prefix.len()..].trim())
}
}

verify_request_claims

The one pipeline both bearer gates run. The verifier holds this server’s origin as the only iss and aud it accepts, and a failure renders through verify_error_response.

The shared authN pipeline both claims-inserting gates run: extract the Authorization: Bearer access token, verify it through the TokenVerifier (signature, iss/aud against the server’s origin, revocation), and map each failure to its response — a missing token is a 401 stamped RequestRefusal::MissingToken, a verify failure whatever errors::verify_error_response maps it to (a rejected or revoked token’s 401 stamped with that refusal). Extracted so require_valid_session and authorization_server_auth_middleware cannot drift in how a token becomes claims; they differ only in the extension type they insert (and the bearer gate’s exempt paths).

The error is the prepared failure Response, boxed so the happy-path Ok stays small (the Response is large — clippy::result_large_err).

#![allow(unused)]
fn main() {
pub(crate) fn verify_request_claims(
    state: &Arc<AuthorizationServerState>,
    headers: &HeaderMap,
    log_context: &'static str,
) -> Result<VerifiedClaims, Box<Response>> {
    let Some(token) = try_bearer_token_from_headers(headers) else {
        return Err(Box::new(errors::unauthorized(RequestRefusal::MissingToken)));
    };
    // The token must name the server's origin. See
    // `docs/Origins/Explanation.md`.
    LiveTokenVerifier::from_state(state)
        .verify(token)
        .map_err(|e| Box::new(errors::verify_error_response(log_context, e)))
}
}

require_valid_session

The session gate on /authorization. It stores the VerifiedClaims in the request, so a token is verified once per request, here, and the Scoped<…> and Authenticated<…> extractors read them.

The /authorization authN gate: verify the request carries a valid, non-revoked bearer token and stash the resulting VerifiedClaims in the request’s extensions for the scope-gated capability extractors (domain::capabilities) to read — a missing/invalid token is a 401.

This layer only proves who the caller is (authN); what they may do (authZ) is decided per-route by the Scoped<…> extractor, which reads these claims and checks the covering scope, returning a 403 with the missing scopes on failure. An Owner token (covering WILDFLOWER_WIDEST_SCOPES) still covers every per-resource scope, so it passes every gate.

This is one of the pair of claims-inserting authN gates (see docs/Authorization/Scope-Gated Endpoints How-To.md, “Wiring the claims”): this one guards the authorization server’s own /authorization router and inserts the domain VerifiedClaims; its sibling authorization_server_auth_middleware wraps the host’s downstream slice routers and inserts the framework-neutral ScopeClaims. Both run the same verify_request_claims pipeline.

Both also stamp the verified OAuth client on the response as a RequestCaller extension, so the host can say which app is using the server over the tunnel. The 401s verify_request_claims answers instead carry a RequestRefusal saying why.

#![allow(unused)]
fn main() {
pub async fn require_valid_session(
    State(state): State<Arc<AuthorizationServerState>>,
    headers: HeaderMap,
    mut req: Request<Body>,
    next: Next,
) -> Response {
    let claims = match verify_request_claims(&state, &headers, "require_valid_session failed") {
        Ok(claims) => claims,
        Err(response) => return *response,
    };
    let caller = RequestCaller {
        client_id: claims.subject.clone(),
    };
    // Hand the verified claims (incl. the `scope` claim) to the handler layer.
    // The scope-gated extractors read them from here rather than re-verifying —
    // authN runs exactly once, at this layer.
    req.extensions_mut().insert(claims);
    let mut response = next.run(req).await;
    // Name the verified caller on the response, for the host's forwarded-request
    // observer (see `wildflowerhealthio_shared_structures::request_caller`).
    response.extensions_mut().insert(caller);
    response
}
}

authorization_server_auth_middleware

The bearer gate the host puts in front of its own routes: the FHIR server, where the paths a client may read without a token are exempt, and the imaging viewer, where none are. A verified request carries the token’s scopes on as ScopeClaims, the framework-neutral form the host’s own Scoped<…> capabilities read.

The downstream-slice authN middleware — 401 for a missing/invalid bearer token, except exempt_paths which pass through (pass &[] to gate every path). Inserts ScopeClaims for downstream Scoped<…> capabilities, and stamps the response with the verified RequestCaller (an exempt path’s response carries none; a 401 carries the RequestRefusal verify_request_claims stamped instead). Clone — build once, clone per router. See docs/Authorization/Scope-Gated Endpoints How-To.md.

#![allow(unused)]
fn main() {
pub fn authorization_server_auth_middleware(
    state: Arc<AuthorizationServerState>,
    exempt_paths: &[&str],
) -> AuthorizationServerAuthMiddleware {
    let gate = BearerGate {
        state,
        exempt: exempt_paths
            .iter()
            .map(|p| p.trim_end_matches('/').to_string())
            .collect(),
    };
    let handler: BearerGateFn = |State(gate), headers, mut req, next| {
        Box::pin(async move {
            if is_exempt(req.uri().path(), &gate.exempt) {
                return next.run(req).await;
            }
            let claims = match verify_request_claims(
                &gate.state,
                &headers,
                "access-token verification failed",
            ) {
                Ok(verified) => verified,
                Err(response) => return *response,
            };
            req.extensions_mut()
                .insert(wildflowerhealthio_scope_capabilities::ScopeClaims::new(
                    claims.scope.clone(),
                ));
            let mut response = next.run(req).await;
            // Name the verified caller on the response, as `require_valid_session`
            // does, for the host's forwarded-request observer.
            response.extensions_mut().insert(RequestCaller {
                client_id: claims.subject,
            });
            response
        })
    };
    axum::middleware::from_fn_with_state(gate, handler)
}
}

http::middleware::authorization_start_limit

The limit sits on the two routes that start a request, GET /oauth/authorize and POST /oauth/device_authorization, on every method axum serves them on, and on no other route. The authorization server doesn’t decide who is over the limit: it knows only the request. The host, which knows the connection a request arrived on, does, through the AuthorizationStartGate port, with an allowance per visitor and one overall.

What spends from the limit is a request raised for the Owner, and only that. Most starts ask the gate at once, before the request is even parsed, so every attempt counts, however malformed. Two kinds of start can’t yet know whether they will reach the Owner, so the layer defers the question and the route asks once it knows:

  • A browser whose session can decide consents, the Owner’s own browser typically. A request it decides on its own consent card raises nothing for the Owner. One it can’t decide, and every device request, does, and asks then.
  • An /oauth/authorize request carrying no browser session. The endpoint sends that browser to pairing and parks nothing, so it costs the Owner no popup, and a flood of them can’t spend the allowance a paired browser’s requests need.

A session the store can’t vouch for, because a store can’t be read, doesn’t defer; it asks the gate like any other start. A request parked on the browser’s limited page has spent by the time it is parked, so going on from that page asks nothing more. Asking the Owner about a request from the consent card raises it without starting one, so it spends from the same limit, when it actually raises one.

limit_authorization_starts

It reads the request’s browser session through carried_browser_session.

Pass request on with a DeferredStartLimit for the route to ask when it carries a live browser session that can decide consents, or when it is a start_route of AuthorizationStartRoute::Authorize that carries no live browser session; pass it on when the state’s AuthorizationStartGate admits it; answer it 429 Too Many Requests, uncached, otherwise.

#![allow(unused)]
fn main() {
pub(crate) async fn limit_authorization_starts(
    State((state, start_route)): State<(Arc<AuthorizationServerState>, AuthorizationStartRoute)>,
    mut request: Request,
    next: Next,
) -> Response {
    let token_verifier = LiveTokenVerifier::from_state(&state);
    let defers = match carried_browser_session(&token_verifier, request.headers()) {
        Ok(Some(claims)) => can_decide_consents(&claims),
        Ok(None) => matches!(start_route, AuthorizationStartRoute::Authorize),
        Err(_) => false,
    };
    if defers {
        let deferred_start_limit = DeferredStartLimit {
            gate: state.authorization_start_gate.clone(),
            request_extensions: request.extensions().clone(),
        };
        request.extensions_mut().insert(deferred_start_limit);
        return next.run(request).await;
    }
    if state.authorization_start_gate.admit(request.extensions()) {
        return next.run(request).await;
    }
    start_limited_response()
}
}

cache_suppress

Every /authorization response is no-store. Each one carries something privileged: a pending consent, a device prompt, the standing grants, the caller’s session, the outcome of an approval. The layer is outermost on the /authorization router, so a new route, a 404 and the session gate’s own 401 all carry it.

Wrap every response flowing through this layer in CacheSuppressed, stamping Cache-Control: no-store + Pragma: no-cache. The headers are inserted (not appended), so a handler that had already set either can’t end up with a duplicate.

}
