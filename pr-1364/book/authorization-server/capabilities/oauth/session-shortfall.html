Session Shortfall

Covers authorization-server-rust/src/domain/capabilities/oauth/session_shortfall.rs

A browser paired with read-only access may run an app that asks for write. A code earned in that browser carries only what its session holds, so the person at the browser is told first, on the limited page, before the Owner is asked anything. The code authorization starter parks such a request awaiting the limited page and sends the browser there. The page reads what the session lacks, and the person goes on (the starter’s continue_past_session_shortfall) or cancels (here).

Every operation answers only the browser session the request was made in, so a leaked request id reads, continues and cancels nothing. No scope opens the capability: the caller is the browser that made the request, known by its browser session, the same PollingBrowserSession the wait page’s poll arrives as.

The tests park code requests from the session shortfall fixtures.

load_code_request_awaiting_limited_page

The one load the page’s read, its Cancel and the starter’s Continue share.

Load request id for the browser session sid while it waits on that browser’s limited page: an unexpired code request made in sid, awaiting the page. Anything else (an unknown id, another session’s request, one gone on, decided or expired) is AuthorizationServerError::AuthorizationRequestNotFound, the status poll’s 404, so the answer says nothing about whether id exists.

#![allow(unused)]
fn main() {
pub(crate) fn load_code_request_awaiting_limited_page(
    tx: &mut impl AuthorizationRequestsTx,
    id: &str,
    sid: &str,
    now: DateTime<Utc>,
) -> Result<CodeRequest, AuthorizationServerError> {
    let not_found = || AuthorizationServerError::AuthorizationRequestNotFound { id: id.to_owned() };
    tx.code_request_by_id(id)?
        .filter(|request| request.is_awaiting_limited_page_at(now) && request.sid == sid)
        .ok_or_else(not_found)
}
}

#![allow(unused)]
fn main() {
pub(crate) fn read(
    &self,
    id: &str,
    browser_session: &PollingBrowserSession,
    now: DateTime<Utc>,
) -> Result<SessionShortfallView, AuthorizationServerError> {
    self.store.read(|tx| {
        let request =
            load_code_request_awaiting_limited_page(tx, id, &browser_session.sid, now)?;
        let client_name = tx
            .client_by_id(&request.client_id)?
            .map_or_else(|| request.client_id.clone(), |client| client.name);
        Ok(SessionShortfallView {
            client_name,
            missing_scopes: session_shortfall(
                &request.requested_scopes,
                &browser_session.grant,
            ),
        })
    })
}
}

cancel

The denial is the request’s own deny_on_limited_page, written through the guarded replace. In the race test, the Cancel’s denial, built from its earlier read, is still a valid transition on paper, but its replace finds the row gone on past the page and writes nothing.

Deny request id, made in the browser session sid, and return the client callback carrying error=access_denied. The denial holds only while the request still waits on the page, so a Continue that went on with it meanwhile wins and this answers not found. The Owner was never told of a request still waiting here, so nothing is republished. A Cancel isn’t remembered: unlike a Continue it records nothing for the session and the client, so the browser’s next request for the client stops at the page again.

#![allow(unused)]
fn main() {
pub(crate) fn cancel(
    &self,
    id: &str,
    sid: &str,
    now: DateTime<Utc>,
) -> Result<String, AuthorizationServerError> {
    let not_found =
        || AuthorizationServerError::AuthorizationRequestNotFound { id: id.to_owned() };
    let cancelled = self.store.write(|tx| {
        let request = load_code_request_awaiting_limited_page(tx, id, sid, now)?;
        let cancelled = request.deny_on_limited_page(now).map_err(|_| not_found())?;
        if tx.replace_code_request(&request, &cancelled)? {
            Ok(cancelled)
        } else {
            Err(not_found())
        }
    })?;
    Ok(build_client_error_redirect_url(
        &cancelled.redirect_uri,
        OAuthErrorCode::AccessDenied,
        REQUEST_DECLINED_DESCRIPTION,
        &cancelled.client_state,
    ))
}
}

A Cancel that read the request before a Continue went on with it doesn’t deny it after: the Continue wins and the Cancel lands nowhere.

#![allow(unused)]
fn main() {
fn a_cancel_racing_a_continue_leaves_the_continued_request_alone() {
    let store = FakeGrantStore::default();
    store
        .tx()
        .insert_code_request(&awaiting_limited_page("req-1"))
        .unwrap();
    let session_shortfall = SessionShortfall::new(store);
    let now = Utc::now();
    let read_by_cancel = load_code_request_awaiting_limited_page(
        &mut session_shortfall.store.tx(),
        "req-1",
        FIXTURE_SID,
        now,
    )
    .expect("the Cancel reads it first");
    let continued = read_by_cancel
        .acknowledge_session_shortfall(Duration::minutes(5), now)
        .expect("the Continue goes on with it");
    assert!(session_shortfall
        .store
        .tx()
        .replace_code_request(&read_by_cancel, &continued)
        .unwrap());
    let cancelled = read_by_cancel
        .deny_on_limited_page(now)
        .expect("the Cancel's read still waits");
    assert!(!session_shortfall
        .store
        .tx()
        .replace_code_request(&read_by_cancel, &cancelled)
        .unwrap());
    assert_eq!(
        status_of(&session_shortfall, "req-1"),
        RequestStatus::Pending
    );
}
}
