Authorize

Covers authorization-server-rust/src/http/routes/oauth/authorize.rs

GET /oauth/authorize is the front door of the authorization-code flow. Nothing in the server calls it. An app finds it in the FHIR server’s .well-known/smart-configuration and sends the person’s browser here, with PKCE and a state. Everything the endpoint answers is for that browser: a redirect onward, or a page saying why it can’t.

No browser session, no authorization. A browser that carries no live browser session is sent to the pairing page first, and nothing is parked, consumed or raised. A browser with one has its request handed to the code authorization starter, which validates it, parks it as a code request made in that session, and says where the browser goes next:

  • back to the app with a code, when a standing grant skips the Owner: the request changes nothing in the app’s registration, the grant covers every requested scope, and the session holds what the request needs or has gone on past the limited page for this app before;
  • to the limited page, when the session holds less than the request asks for and hasn’t gone on for this app;
  • to the consent card, when the browser decides the request itself;
  • to the wait page otherwise, with the request raised for the Owner.

A request that fails once its redirect is trusted goes back to the app with error and state. One that fails while its redirect isn’t trusted gets a local 400 page, since redirecting there would be an open redirect. The Grant Flows, OAuth Endpoints, Session Required and Consent Card integration tests hold the endpoint to each of these answers.

AuthorizeParams

A query missing any of the seven required parameters fails to deserialize, and axum answers its own 400 before the handler runs. The starter checks the values. A launch names a launch context.

Query parameters accepted at /oauth/authorize per RFC 6749 §4.1.1 + RFC 7636 (PKCE). Stricter than the base spec: state is required (the spec merely recommends it), and PKCE with S256 is mandatory — both matching the OAuth 2.1 direction. The optional SMART App Launch extensions (launch, aud) are documented on their fields below.

#![allow(unused)]
fn main() {
pub struct AuthorizeParams {
    /// The response the client wants; only `code` is supported, anything else
    /// is `unsupported_response_type`.
    pub response_type: String,
    /// The PKCE transform (RFC 7636 §4.3); only `S256` is accepted.
    pub code_challenge_method: String,
    /// The client asking. An unknown one is trusted on first use and carried
    /// to the Owner's prompt as a registration warning; a disabled one is
    /// refused on a local page.
    pub client_id: String,
    /// The scopes asked for, space-separated (RFC 6749 §3.3). Scopes outside a
    /// trusted-on-first-use client's registration are carried to the Owner's
    /// prompt; outside a server-defined registration they are refused.
    pub scope: String,
    /// The PKCE challenge, `BASE64URL(SHA256(code_verifier))`, which the code
    /// remembers so `POST /oauth/token` can check the verifier (RFC 7636 §4.2).
    pub code_challenge: String,
    /// Where the browser goes back to with the code or the error. It must be
    /// an http(s) URL; until it is trusted (registered for this client), a
    /// failure renders the local page rather than redirecting there.
    pub redirect_uri: String,
    /// The client's opaque value, carried back unchanged on every redirect to
    /// it. Required here, though RFC 6749 only recommends it.
    pub state: String,
    /// SMART App Launch `launch` value, handed to the app in its launch URL
    /// and forwarded here. It must name a launch this server minted for this
    /// `client_id` that is unused and unexpired (five minutes); it is consumed,
    /// so it works once, and the request carries the launch's context
    /// (including any patient it binds) to the consent. Any other value is
    /// `invalid_request`, its `error_description` saying why. A browser
    /// without a session is sent to pairing before the launch is
    /// read, so pairing never spends it. Absent, the request is plain OAuth.
    pub launch: Option<String>,
    /// SMART App Launch audience: the FHIR server the app expects to call with
    /// the token. When present it must be this server's origin
    /// (`https://<domain>`), which is also its FHIR base, else
    /// `invalid_request`. The minted token's `aud` is the server's origin.
    pub aud: Option<String>,
}
}

handle_authorize_request

It reads the browser session through carried_browser_session before anything else, and passes the starter whether the session can decide consents. may_raise_for_owner asks the deferred start limit, when the layer deferred one; with nothing deferred, the layer has already asked.

The authorization endpoint (RFC 6749 §3.1), the public front door of the OAuth flow. It issues nothing to a browser without a browser session: such a browser is sent to the pairing page first. For a browser with one it validates the request, then either auto-issues an authorization code (when an existing grant pre-approves every requested scope) or parks the user-agent on the consent card or the wait page while the Owner decides.

Nothing in-process calls this route. Registered clients (e.g. SMART-on-FHIR apps) discover it via the FHIR server’s .well-known/smart-configuration (authorization_endpoint) and send the user’s browser here with PKCE params to start an authorization-code flow:

  1. Browser lands here. The browser session cookie is read before anything else: a browser without a live browser session is 302’d to the pairing page, /oauth/pair?next=<this request's path and query>, and nothing is parked, notified or consumed. Once the Owner approves the pairing, the page sends the browser back here with its new session. A browser with a session has its request parked as an AuthorizationRequest (5-minute TTL), made in that session (sid). A SMART App Launch’s aud and launch are checked first (see their fields), and the launch is consumed onto the request.
  2. A request asking for more than the browser’s session holds (scopes a code issued in that session would not carry in full) waits on the limited page at /oauth/authorize/{id}/limited, which says what the session lacks and offers Continue or Cancel: POST /oauth/authorize/{id}/continue goes on as below, POST /oauth/authorize/{id}/cancel answers the client access_denied. Until then the Owner isn’t asked about it. Once a browser session has pressed Continue for a client, its later requests for that client skip the page, whatever the session then lacks.
  3. Unless every requested scope is pre-approved by an existing grant for this (client, redirect_uri) pair, the request joins the pending-consent queue and the browser is 302’d to a page this authorization server serves beside the endpoint, on the origin the browser used. A browser whose session can decide consents and holds the request’s approval scopes goes to the consent card at /oauth/authorize/{id}/consent, where it decides in place; the request records that it can be decided there (decidable_in_requesting_browser). Any other goes to the wait page at /oauth/authorize/{id}/wait, and the Owner is notified (the host webview’s popup). The wait page polls GET /oauth/authorize/{id} (a custom extension, not part of any RFC), which answers the browser session the request was made in and a session that can decide it on the consent card, until the Owner decides — in the popup, in a signed-in launcher, or on the consent card once that browser can decide it. Either way the code is issued under the session the request was made in, not the approver’s. RFC 6749 leaves the owner-interaction mechanism unspecified, so both pages are spec-legal; likewise §4.1 explicitly allows skipping consent on a previously established authorization decision, which is what the grant fast path implements.
  4. Approval 302s the browser back to the client’s redirect_uri with code + state (§4.1.2); the client then redeems the short-lived code at POST /oauth/token (§4.1.3) with its PKCE verifier.

Clients without a server-defined registration are trusted on first use: an unknown client_id, an unregistered redirect_uri, and scopes outside the registration are all carried to the Owner’s prompt as a registration warning rather than rejected here, and nothing is written to the clients table until the Owner approves. Such a request never takes the grant fast path, and while its redirect is untrusted every other failure renders the local HTML page instead of redirecting. A server-defined registration (the host app’s, the FHIR server UI’s) keeps the strict treatment, and a disabled client is rejected either way. Once the redirect is trusted, a failure goes back to the client’s redirect_uri with error, error_description and state (RFC 6749 §4.1.2.1) instead.

The start limit is asked only when it must be: its layer defers a request from a browser that can decide consents, and one carrying no session, and the starter asks the deferred limit only before it raises the request for the Owner or parks it for the limited page.

#![allow(unused)]
fn main() {
pub(super) async fn handle_authorize_request(
    code_authorization_starter: Live<LiveCodeAuthorizationStarter>,
    token_verifier: Live<LiveTokenVerifier>,
    deferred_start_limit: Option<Extension<DeferredStartLimit>>,
    headers: HeaderMap,
    OriginalUri(authorize_uri): OriginalUri,
    Query(params): Query<AuthorizeParams>,
) -> Result<Response, AuthorizeError> {
    // The start limit's layer deferred it for a browser that can decide
    // consents, and for one without a session (sent to pairing below, so it
    // never asks): asked only if the request is raised for the Owner.
    let may_raise_for_owner = || {
        deferred_start_limit
            .as_ref()
            .is_none_or(|Extension(deferred_start_limit)| deferred_start_limit.admits())
    };
    let browser_session = carried_browser_session(&token_verifier, &headers).map_err(|error| {
        AuthorizeError::Internal(InternalError::new(
            "verify a browser session at /oauth/authorize",
            error,
        ))
    })?;
    // No browser session, no authorization: pair this browser first, then
    // come back to this very request. Nothing is parked, notified or consumed.
    let Some((browser_session, browser_sid)) = browser_session
        .as_ref()
        .and_then(|claims| Some((claims, claims.sid.as_deref()?)))
    else {
        return Ok(found_redirect(&pairing_page_location(
            authorize_uri
                .path_and_query()
                .map_or(authorize_uri.path(), |path_and_query| {
                    path_and_query.as_str()
                }),
        )));
    };
    let browser_session_grant = browser_session.granted();
    let next_step = code_authorization_starter.start(
        &AuthorizeRequest {
            response_type: &params.response_type,
            code_challenge_method: &params.code_challenge_method,
            client_id: &params.client_id,
            scope: &params.scope,
            code_challenge: &params.code_challenge,
            redirect_uri: &params.redirect_uri,
            client_state: &params.state,
            launch: params.launch.as_deref(),
            aud: params.aud.as_deref(),
            browser_session_grant: &browser_session_grant,
            can_decide_consents: can_decide_consents(browser_session),
            may_raise_for_owner: &may_raise_for_owner,
            sid: browser_sid,
        },
        FreshIds {
            request_id: Uuid::new_v4().to_string(),
            code: generate_authorization_code(),
        },
        chrono::Utc::now(),
    )?;
    Ok(found_redirect(&next_step_location(next_step, "")))
}
}

next_step_location

The pages’ locations come from consent_page_location, wait_page_location and limited_page_location; the app’s from the domain’s build_client_redirect_url.

Where next_step sends the browser: straight back to the client with the fresh code when fully pre-approved (RFC 6749 §4.1.2), else to a page for the request, relative to /oauth/ (request_page_location) after page_prefix: empty for /oauth/authorize’s own Location, which the browser resolves against the endpoint, and /oauth/ for the limited page’s Continue, which the page follows from elsewhere.

The Owner decides on the consent card when this browser can decide the request, and else from this authorization server’s wait page, which waits for whichever surface — the host popup, a signed-in launcher’s consent list, or the consent card — decides first. A browser whose session holds less than the app asks for is first told so on the limited page, which goes on or cancels.

#![allow(unused)]
fn main() {
pub(super) fn next_step_location(next_step: AuthorizeNextStep, page_prefix: &str) -> String {
    let request_page = match next_step {
        AuthorizeNextStep::RedirectToClient {
            redirect_uri,
            code,
            client_state,
        } => return build_client_redirect_url(&redirect_uri, &code, &client_state),
        AuthorizeNextStep::AwaitOwner {
            request_id,
            decidable_in_requesting_browser: true,
        } => consent_page_location(&request_id),
        AuthorizeNextStep::AwaitOwner {
            request_id,
            decidable_in_requesting_browser: false,
        } => wait_page_location(&request_id),
        AuthorizeNextStep::ConfirmSessionShortfall { request_id } => {
            limited_page_location(&request_id)
        }
    };
    format!("{page_prefix}{request_page}")
}
}

AuthorizeError

Error half of the /oauth/authorize handler’s Result. Each variant renders one of the endpoint’s failure responses through IntoResponse, so a fallible step bails with ? instead of a match + return at every call site — the authorization-endpoint analogue of TokenError (and, on the Owner /authorization surface, AuthorizationServerError). Kept small (no embedded Response) so Result<_, AuthorizeError> doesn’t trip clippy::result_large_err.

#![allow(unused)]
fn main() {
pub(super) enum AuthorizeError {
    /// A failure on a request whose `redirect_uri` is not trusted — a disabled
    /// client, a malformed or non-http(s) URI, an unregistered redirect for a
    /// server-defined registration, or (because the client is new to this authorization server or
    /// the redirect is not on its registration) any later validation failure.
    /// Renders a `400` with the server's own HTML error page
    /// ([`oauth_error_html`]) — redirecting to an unvouched-for URI would be
    /// an open redirect (RFC 6749 §4.1.2.1).
    LocalPage(AuthorizeRefusal),
    /// A spec'd error once `redirect_uri` is validated — 302 back to the
    /// client. Carries the already-built `Location` (the client `redirect_uri`
    /// merged with `error` + `error_description` + `state`, RFC 6749
    /// §4.1.2.1) rather than the `Url`, keeping the variant small enough to
    /// dodge `clippy::result_large_err`.
    Redirect {
        /// The client's `redirect_uri` with the error, its description and
        /// the client's `state` in its query.
        location: String,
    },
    /// No active signing key: without token-mint capability the endpoint can't
    /// proceed, so it 503s rather than parking a request it can never complete.
    /// Nothing is parked.
    ServiceUnavailable,
    /// The authorization start limit refused a request that would be raised
    /// for the Owner — the `429` the limit's layer answers.
    StartLimited,
    /// A logged, opaque 500 — see [`InternalError`]. A store failure, or a
    /// request the fast path found no longer pending when it came to approve
    /// it.
    Internal(InternalError),
}
}

from

The starter’s failures map onto it. A redirectable one has its Location built here, with build_client_error_redirect_url. A request the fast path found no longer pending, and a store failure, are both logged 500s.

Render the flow’s failure vocabulary onto the endpoint’s responses: a local page while the redirect is untrusted, a 302 with error + error_description + state back to a validated redirect (RFC 6749 §4.1.2.1), a 503 with no signing key, the start limit’s 429, and a logged opaque 500 for the rest.

#![allow(unused)]
fn main() {
fn from(error: AuthorizationStartError) -> Self {
    match error {
        AuthorizationStartError::NoActiveSigningKey => AuthorizeError::ServiceUnavailable,
        AuthorizationStartError::StartLimited => AuthorizeError::StartLimited,
        AuthorizationStartError::LocalPage(kind) => {
            if kind == AuthorizeRefusal::RedirectUriNotAllowed {
                tracing::warn!("redirect_uri not on a server-defined registration");
            }
            AuthorizeError::LocalPage(kind)
        }
        AuthorizationStartError::Redirectable {
            redirect_uri,
            error,
            description,
            client_state,
        } => AuthorizeError::Redirect {
            location: build_client_error_redirect_url(
                &redirect_uri,
                error,
                description,
                &client_state,
            ),
        },
        AuthorizationStartError::RequestNotPending => {
            AuthorizeError::Internal(InternalError::new(
                "approve_authorization_request",
                "authorization request was not pending",
            ))
        }
        AuthorizationStartError::Store(error) => AuthorizeError::Internal(InternalError::new(
            "store operation failed at /oauth/authorize",
            error,
        )),
    }
}
}

fn main() {
fn into_response(self) -> Response {
    match self {
        AuthorizeError::LocalPage(kind) => html_bad_request(oauth_error_html(kind)),
        AuthorizeError::Redirect { location } => found_redirect(&location),
        AuthorizeError::ServiceUnavailable => StatusCode::SERVICE_UNAVAILABLE.into_response(),
        AuthorizeError::StartLimited => start_limited_response(),
        AuthorizeError::Internal(error) => error.into_response(),
    }
}
}
