Browser Session Cookie

Covers authorization-server-rust/src/http/browser_session_cookie.rs

A browser the server has let in holds its browser session in a cookie, __Host-browser_session. The cookie’s value is the browser’s access token itself, issued to the browser-session client and naming the session as its sid. Nothing about the cookie is stored server-side: a restart doesn’t sign the browser out, and what does is whatever the token verifier refuses: a revoked jti, a revoked subject, or a revoked browser session.

The server sets the cookie when it signs a browser in: the Owner’s at same-device sign-in, an approved browser’s on the pairing page’s poll. From then on two kinds of reader use it:

  • The host’s cookie-to-bearer layer, in front of everything, turns the cookie of a request from the server’s own pages into that request’s bearer, so the gates check it like any other token. It asks this file whether the session still stands, records the use, and clears the cookie once the session has ended.
  • The front door reads it directly: /oauth/authorize sends a browser with no standing session to pairing and issues an app’s code under the session it finds; the wait page’s status poll and the limited page’s calls read it to know whose browser is asking; the start limit reads it to decide whether to defer; sign-out reads it to know which session to end.

A browser can also hold the FHIR web UI’s hfs_session. When both ride a request, the host’s layer presents hfs_session’s bearer, unless the page names the browser session with the SESSION_HEADER.

standing_browser_session

Does this cookie value still hold a browser session? A token the verifier refuses as rejected or revoked is None, not an error; only a store that can’t be read is an error, so the caller can tell “signed out” from “can’t tell”. The host’s cookie-to-bearer layer calls this with the cookie’s value.

The verified claims of the browser session a browser session cookie holds, or None once the session has ended: the gates would refuse session_token as a bad, expired or revoked token (by its jti, its subject or its browser session), checked by the same TokenVerifier the gates run, or it is no browser session’s token at all. Their sid names the browser session.

Errors

The server-side AccessTokenVerifyErrors, when a key, revocation or browser-session store can’t be read, so the session can’t be checked.

    session_token: &str,
) -> Result<Option<VerifiedClaims>, AccessTokenVerifyError> {
    standing_session_claims(&LiveTokenVerifier::from_state(state), session_token)
}

standing_session_claims

The decision itself, over any store, which the test drives directly. Any token but a browser-session client’s under a session holds none, even one the gates would accept: an app’s token copied into the cookie doesn’t make a browser session. The tests mint real tokens and verify them against the fake store.

The verified claims of session_token, or None when it holds no standing browser session: token_verifier refuses it for good (bad, expired or revoked), or it is some other token, not issued to the browser-session client under a browser session (its sid).

Errors

The server-side AccessTokenVerifyErrors, when a store can’t be read.

#![allow(unused)]
fn main() {
fn standing_session_claims<S: GrantStore>(
    token_verifier: &TokenVerifier<S>,
    session_token: &str,
) -> Result<Option<VerifiedClaims>, AccessTokenVerifyError> {
    match token_verifier.verify(session_token) {
        Ok(claims) if claims.subject == BROWSER_SESSION_CLIENT_ID && claims.sid.is_some() => {
            Ok(Some(claims))
        }
        Ok(_) | Err(AccessTokenVerifyError::TokenRejected | AccessTokenVerifyError::Revoked) => {
            Ok(None)
        }
        Err(error) => Err(error),
    }
}
}

Only a token issued to the browser-session client under a standing browser session is one: another client’s token the gates would accept, even under that session, and a browser-session client’s token with no session, hold no browser session.

#![allow(unused)]
fn main() {
fn only_a_browser_session_token_holds_a_browser_session() {
    let store = FakeGrantStore::default();
    let key = seed_active_signing_key(&store);
    let session =
        BrowserSession::new_same_device_session(vec![], Duration::hours(8), Utc::now());
    store.tx().insert_browser_session(&session).expect("insert");
    let verifier = TokenVerifier::new(store, Arc::new(NothingRevoked), ORIGIN.into());

    let browser_session_token = mint(&key, BROWSER_SESSION_CLIENT_ID, Some(&session.sid));
    let claims = standing_session_claims(&verifier, &browser_session_token)
        .expect("checked")
        .expect("a browser session");
    assert_eq!(claims.sid.as_deref(), Some(session.sid.as_str()));
    for (token, case) in [
        (mint(&key, "another-client", None), "another client's token"),
        (
            mint(&key, "another-client", Some(&session.sid)),
            "another client's token under the session",
        ),
        (
            mint(&key, BROWSER_SESSION_CLIENT_ID, None),
            "a browser-session client token without a sid",
        ),
    ] {
        assert!(
            standing_session_claims(&verifier, &token)
                .expect("checked")
                .is_none(),
            "{case} holds no browser session"
        );
    }
}
}

browser_session_token

It parses every Cookie header, so a browser sending its cookies in one header or several is read the same, and matches the name exactly. The test builds its headers with cookie_headers.

The browser session cookie’s value among headers’ Cookies, if the browser sent it.

#![allow(unused)]
fn main() {
fn browser_session_token(headers: &HeaderMap) -> Option<String> {
    headers
        .get_all(header::COOKIE)
        .iter()
        .filter_map(|cookie_header| cookie_header.to_str().ok())
        .flat_map(Cookie::split_parse)
        .filter_map(Result::ok)
        .find(|cookie| cookie.name() == BROWSER_SESSION_COOKIE)
        .map(|cookie| cookie.value().to_owned())
}
}

can_decide_consents

The Owner’s session can; a browser paired with less can’t. This is a necessary condition, not the whole one: whether a given request goes to the consent card also depends on the session holding that request’s approval scopes, which /oauth/authorize works out per request. The start limit uses it to decide whether a start can wait to be counted (see limit_authorization_starts).

Whether the browser session claims describe can decide consents: its grant covers both loading a request on the consent card (consent_reader_scopes) and deciding it (consent_decider_scopes). A request such a browser starts is sent to the consent card and decided there when the session also holds that request’s approval scopes (as /oauth/authorize works out per request); otherwise it goes to the wait page and is raised for the Owner, and only then does its start spend from the authorization start limit.

#![allow(unused)]
fn main() {
pub(crate) fn can_decide_consents(claims: &VerifiedClaims) -> bool {
    let granted = claims.granted();
    consent_reader_scopes()
        .iter()
        .chain(&consent_decider_scopes())
        .all(|required| granted.covers(required))
}
}
