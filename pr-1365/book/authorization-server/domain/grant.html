Wildflower, Read in Order

Grant

Covers authorization-server-rust/src/domain/grant.rs

A grant is the Owner’s standing yes. When the Owner approves an app’s request, the server records a grant alongside the one-off approval: “this app may have these scopes, here”. The grant lasts until the Owner revokes it. Nothing about it expires.

There are two kinds, one per flow that has an Owner to ask. An authorization-code grant is keyed on the app and the exact redirect URI it asked from. A device grant is keyed on the app and the device’s name. It is the Owner’s record of which devices they have paired, and it never skips a prompt.

When a grant skips the Owner

A later request from the same app, at the same redirect, may get its code at /oauth/authorize without asking the Owner. That takes all of these at once:

  • The request changes nothing in the app’s registration: its presented client change is NoChange. A new app, a new redirect or a new scope always goes back to the Owner, however much an old grant covers.
  • The standing grant covers every requested scope. A grant that covers only some of them pre-ticks those on the consent card, and the Owner decides the rest.
  • The request’s browser session holds what the request needs, or has gone on past its limited page for this app before, so the request isn’t waiting there. The code then carries only what the session also covers.
  • A launch’s patient, if it bound one, is the grant’s patient. Otherwise the Owner decides.

The proof that the first two hold is GrantCoverage::resolve; the request’s limited page is on the Code Request page. A code issued this way stamps the grant’s last_used_at. A device grant’s is stamped instead when a refresh family it earned rotates.

Revoking a grant ends what it earned. GrantsRevoker::revoke revokes every access token the app holds, deletes the row, and expires every refresh family issued to the app.

domain::grant

AuthorizationCodeGrant

A standing authorization-code consent: client X may have scopes Y at redirect URI Z. A later request from the client at that redirect gets its code without asking the Owner only when it changes nothing in the client’s registration, this grant covers every requested scope, its browser session is live and holds what it asks for (or its browser has gone on past the limited page for this client), and a launch’s patient, if any, is this grant’s. A grant covering only some scopes pre-ticks them on the consent card.

One grant per (client_id, redirect_uri). Diesel-mapped 1:1 to the authorization_code_grants table; on the wire it rides inside Grant::AuthorizationCode.

#![allow(unused)]
fn main() {
pub struct AuthorizationCodeGrant {
    /// Primary key — a UUID minted at first upsert, unique across BOTH grant
    /// tables (so a bare grant id read through the `grants` view is
    /// unambiguous).
    pub id: String,
    /// `client_id` the Owner approved this grant for.
    pub client_id: String,
    /// Everything the Owner has approved for this client at this redirect,
    /// across every approval; consent is cumulative (see
    /// [`CumulativeConsent`]).
    pub scopes: Vec<String>,
    /// When the Owner gave (or last re-confirmed) consent: the latest
    /// approval.
    pub granted_at: DateTime<Utc>,
    /// When this grant last let a code be issued without asking the Owner,
    /// at `/oauth/authorize` or at the limited page's Continue; `None` until
    /// it first does. A re-approval keeps it.
    pub last_used_at: Option<DateTime<Utc>>,
    /// The SMART patient the latest approval named, carried forward to the
    /// codes this grant lets be issued without asking the Owner.
    pub patient: Option<String>,
    /// The exact redirect URI this grant covers — `/authorize` keys the
    /// consent-skip fast path on `(client_id, redirect_uri)`.
    pub redirect_uri: Url,
}
}

DeviceGrant

A standing device pairing: the durable record of an approved device-code flow, keyed on the client and the human-facing device name. It is the Owner’s record of which devices they have paired; it never skips a prompt. A refresh family begun by the device’s poll records the grant’s id. Diesel-mapped 1:1 to the device_grants table; on the wire it rides inside Grant::DeviceCode.

    /// tables.
    pub id: String,

    pub client_id: String,
    /// Scopes the Owner approved; consent is cumulative (see
    /// [`CumulativeConsent`]).
    pub scopes: Vec<String>,
    /// When the Owner gave (or last re-confirmed) consent: the latest

    /// The SMART patient the latest approval named, if any.
    pub patient: Option<String>,
    /// The human-facing device name this pairing is keyed on. Defaults to
    /// the client's name when the device didn't name itself.
    pub device_name: String,
}
}

CumulativeConsent

The re-approval rule both grant kinds share — behaviour, not structure: consent is cumulative. A later approval unions its scopes into the standing set (order-preserving, no duplicates) and refreshes the consent instant and patient context; approving a narrower request never withdraws previously-consented scopes — revoking the grant is the way to withdraw.

#![allow(unused)]
fn main() {
pub trait CumulativeConsent {
    /// Fold a re-approval into this standing grant: union `additional` scopes
    /// in, stamp `granted_at = at`, and adopt the re-approval's `patient`.
    /// `last_used_at` is left as it was.
    fn absorb_reapproval(
        &mut self,
        additional: &[String],
        patient: Option<&str>,
        at: DateTime<Utc>,
    );
}
}

The shared re-approval behaviour: scopes union (order-preserving, no duplicates — a narrower re-approval withdraws nothing), and the consent instant + patient context refresh. Exercised through the trait so both kinds share one rule.

#![allow(unused)]
fn main() {
fn absorb_reapproval_unions_scopes_and_refreshes_consent() {
    let later: DateTime<Utc> = "2025-06-01T00:00:00Z".parse().expect("timestamp");

    let mut code = code_grant();
    code.absorb_reapproval(
        &["read".to_owned(), "write".to_owned()],
        Some("pat-2"),
        later,
    );
    assert_eq!(
        code.scopes,
        vec![
            "read".to_owned(),
            "offline_access".to_owned(),
            "write".to_owned()
        ],
    );
    assert_eq!(code.granted_at, later);
    assert_eq!(code.patient.as_deref(), Some("pat-2"));

    let mut device = device_grant();
    device.absorb_reapproval(&["read".to_owned()], None, later);
    assert_eq!(
        device.scopes,
        vec!["read".to_owned(), "offline_access".to_owned()],
        "a narrower re-approval never un-approves earlier consent",
    );
    assert_eq!(device.granted_at, later);
    assert_eq!(device.patient, None);
}
}

fn absorb_reapproval_records_one_scope_per_resource_not_two_spellings() {

    let mut code = code_grant();

union_scopes_into

Widen standing by additional — the shared half of CumulativeConsent.

wildflowerhealthio_scopes::widened_scopes, not a string union: the scopes are parsed, so re-approving patient/Patient.cruds over a standing patient/Patient.r records the one broader consent instead of accumulating both spellings, and re-approving what is already consented leaves the row byte-identical. The standing set still only ever grows — the widened list reaches every interaction it reached before.

#![allow(unused)]
fn main() {
fn union_scopes_into(standing_ref: &mut Vec<String>, additional: &[String]) {
    *standing_ref = wildflowerhealthio_scopes::widened_scopes(standing_ref, additional);
}
}

Grant

The wire/list seam over the two concrete grant kinds — what cross-kind reads (all_grants, grant_by_id) return and what the /authorization/grants endpoints serialize. Internally-tagged on grantType with the snake_case kind names, so each variant serializes as its struct’s camelCase fields with the tag alongside — the exact grantType-tagged union the TS access-management GrantSchema decodes (pinned by the tests below).

    DeviceCode(DeviceGrant),
}
}
