Delegated Scopes

Covers authorization-server-rust/src/domain/authority/delegated_scopes.rs

When a request is approved, someone is handing on access: the Owner, or a browser the Owner paired. No one can delegate more than they hold. This page holds the scope rules the whole server leans on for that, in three parts.

  • What a prompt may grant at most. Each consent prompt has a ceiling, set by its flow and the app’s registration. Whatever the approver ticks is clamped to it.
  • What the approver must hold. To approve a prompt at all, the approver holds its approval scopes: the power to decide the request and to create what approving it creates. And every piece of access it passes on, it must hold itself.
  • What the browser holds. A code issued for an app carries only what the browser session the request was made in also holds, and the browser is told beforehand what it lacks, on the limited page.

Delegated scopes are the proof of the first two: a scope set the approver has approved and is entitled to delegate. The writers that record grants, write registrations and issue codes on an approval accept nothing else. The third part is two free functions, applied when a code is issued and when /oauth/authorize decides where to send the browser.

Every “covers” on this page is the scope coverage the Scopes page explains: by permission, not by spelling.

ApprovalFlow

A prompt belongs to one of three flows, and the flow decides both its ceiling and its approval scopes.

The flow a consent prompt belongs to, which decides its ceiling, its approval scopes, and whether approving it writes the client registration.

  • A code prompt for a client trusted on first use records a grant, writes the registration, and its approver must hold what is asked.
  • A code prompt for a server-defined (fixed) registration records a grant and its approver must hold what is asked, but it writes no registration.
  • A device prompt records a grant only; its consent is expandable, so the approver need not hold what the device asked for.
  • A browser pairing records no grant and writes no registration; like a device prompt it is expandable.
#![allow(unused)]
fn main() {
enum ApprovalFlow {
    /// An authorization-code prompt, whose approval records a standing grant
    /// and approves the request as asked.
    Code {
        /// Whether the client's registration is server-defined, which an
        /// approval never writes. When it is not, the client is trusted on
        /// first use, so approving creates or widens its registration.
        registration_is_fixed: bool,
    },
    /// A device-code prompt: approving records a standing device grant.
    Device,
    /// A browser pairing: approving records no grant and registers no client.
    BrowserPairing,
}
}

ApprovableScopes

The scopes one consent prompt may grant at most, decided by its flow. An approved scope must be covered by a scope of the request and by a scope of the registration ceiling (the most the client’s registration permits for this approval); each constructor names the policy that fills those two halves.

The flow also decides the prompt’s approval scopes, what its approver must hold to approve it at all (missing_approval_scopes).

#![allow(unused)]
fn main() {
pub(crate) struct ApprovableScopes {
    /// The half that bounds a tick by what was asked: the request's scopes for
    /// a code prompt, so a code prompt never grants past what the client asked
    /// for. An expandable prompt fills it with its ceiling instead: a device
    /// prompt's registered scopes, a pairing's the Owner's scopes.
    requested_scopes: Vec<String>,
    /// The most the client's registration permits for this approval: a fixed
    /// registration's scopes, a registration trusted on first use's scopes
    /// plus what the request asks for, a device client's registered scopes, or
    /// the Owner's scopes for a pairing.
    registration_ceiling_scopes: Vec<String>,
    /// The prompt's flow, which sets its approval scopes and whether approving
    /// it writes the registration.
    flow: ApprovalFlow,

for_code

Who defines the registration decides the ceiling (is_registration_fixed). Either way the request is the other half, so a code prompt never grants past what the app asked for. A resolved code request builds its prompt here.

An authorization-code prompt for requested_scopes. A fixed (server-defined) registration is its own ceiling; any other client is trusted on first use, so its ceiling also takes in what this request asked for — its registration is widened with the grant.

#![allow(unused)]
fn main() {
pub(crate) fn for_code(
    requested_scopes: &[String],
    maybe_existing_client: Option<&Client>,
    registration_is_fixed: bool,
) -> Self {
    let registered_client_scopes = maybe_existing_client
        .iter()
        .flat_map(|existing_client| existing_client.allowed_scopes.iter().cloned());
    let registration_ceiling_scopes = if registration_is_fixed {
        registered_client_scopes.collect()
    } else {
        registered_client_scopes
            .chain(requested_scopes.iter().cloned())
            .collect()
    };
    ApprovableScopes {
        requested_scopes: requested_scopes.to_vec(),
        registration_ceiling_scopes,
        flow: ApprovalFlow::Code {
            registration_is_fixed,
        },
    }
}
}

missing_approval_scopes

One function answers “may this approver approve?” for every place that asks, so the consent card, the approve route and /oauth/authorize never disagree.

The prompt’s approval scopes the approver_grant does not cover, rendered, in order; empty when it may approve. Shared by the approve paths (through DelegatedScopes::clamp), the consent read (missingApprovalScopes), and /oauth/authorize’s choice between the consent card and the wait page, so the three never disagree.

The approval scopes, and who takes them:

  • wildflower/AuthorizationRequest.u: every approval, to decide the request at all.
  • wildflower/Grant.c: a code or device approval, which records a standing grant; a browser pairing records none.
  • wildflower/Client.c and wildflower/Client.u: a code approval for a client trusted on first use, which creates or widens its registration, whichever the row needs when the approval lands; a server-defined registration takes neither.
  • Each held access (is_held_access) the request asks for that the prompt may grant: a code approval, which approves the request as asked, else it goes to the Owner.

A device or pairing prompt is expandable, so its approver may grant whatever it holds, and DelegatedScopes::clamp bounds that scope by scope instead. The Owner’s scopes lack no approval scope on any prompt.

#![allow(unused)]
fn main() {
pub(crate) fn missing_approval_scopes(&self, approver_grant: &Grant) -> Vec<String> {
    let mut approval_scopes = consent_decider_scopes();
    if self.flow.would_record_grant() {
        approval_scopes.extend(grant_creating_approval_scopes());
    }
    if self.flow.would_write_registration() {
        approval_scopes.extend(client_registering_approval_scopes());
    }
    let uncovered_approval_scopes: Vec<Scope> = approval_scopes
        .into_iter()
        .filter(|required| !approver_grant.covers(required))
        .collect();
    let mut missing = render_scopes(&uncovered_approval_scopes);
    if self.flow.would_approve_as_asked() {
        missing.extend(uncovered_held_access(
            &self.grantable_subset(self.requested_scopes.clone()),
            approver_grant,
        ));
    }
    missing
}
}

clamp

The one constructor. It runs missing_approval_scopes first, then grantable_subset, then uncovered_held_access against the approver’s grant. A held access the approver lacks fails the whole approval, rather than being dropped in silence, so the Owner sees the refusal instead of a narrower grant than they ticked.

The approval rule, in three steps:

  1. Require that the approver_grant holds the approvable prompt’s approval scopes (missing_approval_scopes), whatever was ticked, even nothing.
  2. Clamp the owner_approved_scopes to the approvable scopes’ grantable subset: Ok(None) when nothing survives, and the caller denies rather than recording an empty grant.
  3. Require that the approver_grant covers every held access (is_held_access) that survives, in either spelling; one it lacks fails the whole approval, naming it.

Identity and session markers (openid, offline_access, …) are no held access and pass the approver check; a resource scope or wildflower/launch the approver lacks fails the whole approval (a 403) rather than being silently dropped. Coverage is checked across both SMART spellings via Scope::as_alternate_canonical_form, the twinning the token minter applies.

AuthorizationServerError::InsufficientScope naming the approval scopes the approver lacks, checked first, whatever was ticked; then AuthorizationServerError::InsufficientApproverScope naming the held access the approver cannot delegate.

#![allow(unused)]
fn main() {
pub(crate) fn clamp(
    approver_grant: &Grant,
    owner_approved_scopes: Vec<String>,
    approvable: &ApprovableScopes,
) -> Result<Option<Self>, AuthorizationServerError> {
    let missing_scopes = approvable.missing_approval_scopes(approver_grant);
    if !missing_scopes.is_empty() {
        return Err(AuthorizationServerError::InsufficientScope { missing_scopes });
    }
    let grantable = approvable.grantable_subset(owner_approved_scopes);
    if grantable.is_empty() {
        return Ok(None);
    }
    let approver_missing_scopes = uncovered_held_access(&grantable, approver_grant);
    if approver_missing_scopes.is_empty() {
        Ok(Some(DelegatedScopes {
            scopes: grantable,
            writes_registration: approvable.flow.would_write_registration(),
        }))
    } else {
        Err(AuthorizationServerError::InsufficientApproverScope {
            approver_missing_scopes,
        })
    }
}
}

session_bounded_scopes

A code carries only what both the app’s authority and the browser the request was made in allow. The request’s approval and the standing grant keep the authorized scopes; only the code is narrowed. So a browser paired read-only earns no app write access, whoever approved the request.

The authorized scopes narrowed to what the browser session holding session_grant also holds: an authorization code carries only what both the client’s authority and the browser the request was made in allow.

Held access (is_held_access) the session covers, by the rule DelegatedScopes::clamp holds an approver to (either SMART spelling, system/* covering patient/* and user/*), stays as authorized. Held access the session covers only in part narrows to the parts it holds: its intersection with each session scope (intersection_in_either_spelling), so system/*.cruds against a session holding system/Patient.cruds yields system/Patient.cruds. A part is spelled in the authorized scope’s grammar where one spells it, and in letters where no word does. wildflower/launch has no parts, so it stays only when the session holds it. Identity and session markers are no held access, so they pass through.

One scope’s parts are collapsed (Grant::collapse), so overlapping session scopes yield the broadest part once, and the result keeps each scope’s first occurrence, in order. A session that covers everything authorized changes nothing but exact duplicates.

#![allow(unused)]
fn main() {
pub(crate) fn session_bounded_scopes(authorized: &[String], session_grant: &Grant) -> Vec<String> {
    let session_covers = coverage_in_either_spelling(session_grant);
    let mut already_bounded = HashSet::new();
    let bounded: Vec<Scope> = authorized
        .iter()
        .map(|rendered| Scope::from(rendered.as_str()))
        .flat_map(|authorized_scope| {
            if !is_held_access(&authorized_scope) || session_covers(&authorized_scope) {
                vec![authorized_scope]
            } else {
                let mut parts = Grant::new(
                    session_grant
                        .scopes
                        .iter()
                        .filter_map(|session_scope| {
                            intersection_in_either_spelling(&authorized_scope, session_scope)
                        })
                        .collect(),
                );
                parts.collapse();
                parts.scopes
            }
        })
        .filter(|scope| already_bounded.insert(scope.clone()))
        .collect();
    render_scopes(&bounded)
}
}

fn main() {
fn intersection_in_either_spelling(
    authorized_scope: &Scope,
    session_scope: &Scope,
) -> Option<Scope> {
    let authorized_spellings = [
        Some(authorized_scope.clone()),
        authorized_scope.as_alternate_canonical_form(),
    ];
    // The session's letter form first, so a letter-spelled authorized scope
    // intersects to a letter bag rather than the session's word.
    let session_spellings = [
        session_scope.as_alternate_canonical_form(),
        Some(session_scope.clone()),

    authorized_spellings
        .iter()
        .flatten()
        .find_map(|authorized_spelling| {
            session_spellings
                .iter()
                .flatten()
                .find_map(|session_spelling| authorized_spelling.intersection(session_spelling))
        })
}
