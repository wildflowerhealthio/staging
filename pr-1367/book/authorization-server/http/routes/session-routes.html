Four routes are about tokens themselves rather than what they unlock. A caller reads back its own session and ends it. The Owner revokes tokens, by id or by app. Anyone fetches the public keys that verify every token this server signs.

The first three live under /authorization, behind require_valid_session: no valid, unrevoked bearer token, no answer but a 401. The session read and logout are self-service: a caller acting on its own session needs no scope, so they take their capability through Authenticated<…>, which hands over the caller’s verified claims and nothing else. Revoking other tokens is an Owner’s power, and takes wildflower/Token.d through Scoped<…>. The key set is public, and sits outside /authorization.

http::routes::session

GET /authorization/session — the caller reading back their own session.

Self-service, authN-only, exactly like logout: every field is derived from the token the caller already presented, or from the browser session it was minted under, so the response can’t disclose anything about another caller, and no Scoped<…> capability gates it — the /authorization mount’s require_valid_session gate is the whole authorization it needs. That is load-bearing rather than merely convenient: the callers who need this most are under-scoped sessions (one that just took a 403 InsufficientScope), and any admin scope gate would lock exactly those out of reading their own scopes.

The device-login screen reads it to seed the scope picker from the session’s real scopes rather than a hard-coded preset — the device flow mints a whole new grant, so a step-up seeded from anything narrower silently drops access the caller already had. The server’s own pages read it for when this browser’s session expires, which they show as “Signed in until”. See the Scope-Gated Endpoints How-To.

http::routes::logout

POST /authorization/logout — ends the caller’s session by revoking the presented access token and redirecting to the hosted launcher.

Self-service, authN-only: logout is a caller ending their own session, not an admin resource operation, so it takes no scope — the /authorization mount’s require_valid_session gate (any valid, non-revoked bearer) is the whole authorization it needs, and it acts on the already-verified claims through the authenticated-only LiveSessionEnder rather than re-verifying. The access token is a stateless JWT that keeps its own short TTL; the client forgetting it ends the session in that client, so logout also revokes the presented token’s jti in the shared store, closing the window a leaked copy could otherwise ride until exp.

handle_logout

The session ender is built from the claims require_valid_session already verified, and end denylists the token’s jti. Denylisting is best-effort: a token with no jti or expiry has nothing to denylist, and a store failure is logged, never answered. Either way the browser goes to the hosted launcher with a 303 See Other, which turns the POST into a GET.

POST /authorization/logout: denylist the presented token’s jti through Authenticated<LiveSessionEnder>, then answer 303 See Other to the hosted launcher’s root.

#![allow(unused)]
fn main() {
async fn handle_logout(session: Authenticated<LiveSessionEnder>, pages: LauncherPages) -> Response {
    // Revoke the presented session token so a leaked copy can't outlive the
    // logout. Best-effort by design: a store hiccup must never fail the logout.
    session.end();
    // `303 See Other` → the hosted launcher's root (this server serves no UI of
    // its own); `303` downgrades a `POST` logout to a `GET`.
    Redirect::to(pages.root_url()).into_response()
}
}

http::routes::revocations

POST /authorization/revocations — the token-revocation control surface. Acquired through the LiveTokenRevoker facade (scope wildflower/Token.d): a caller must cover the Token delete scope — which an owner’s wildflower/*.cruds does — to revoke, else a 403.

Two modes, exactly one per request:

  • Per-token — { "jti": "…", "expiresAt": "<RFC3339>" } denylists a single token until its own expiry (the expiresAt lets the background sweep drop the row once the token would have expired anyway).
  • Bulk, per subject — { "subject": "<client_id>" } bumps the subject’s revocation epoch to just past now (see revoke_subject_as_of_now), invalidating every token that subject holds issued at or before the call — including one minted in the current (second-granular) second. subject is the sub claim (the client_id), so revocation is per client, not per device.

The daily sweep keeps a denylisted jti until the longest token this server mints, issued at the moment of revocation, would have expired (see setup_authorization_server). So an expiresAt that is too early can’t free a live token.

into_revocation

Collapse the optional wire fields into exactly one Revocation mode, or a 400 for a body that names neither, both, or an incomplete mode.

#![allow(unused)]
fn main() {
fn into_revocation(self) -> Result<Revocation, RevocationError> {
    match (self.jti, self.subject) {
        (Some(jti), None) => {
            let expires_at = self.expires_at.ok_or_else(|| {
                RevocationError::bad_request(
                    "MissingExpiresAt",
                    "revoking by `jti` requires `expiresAt` (the token's own expiry)",
                )
            })?;
            Ok(Revocation::Token { jti, expires_at })
        }
        (None, Some(subject)) => Ok(Revocation::Subject { subject }),
        (Some(_), Some(_)) => Err(RevocationError::bad_request(
            "AmbiguousRevocation",
            "provide exactly one of `jti` or `subject`, not both",
        )),
        (None, None) => Err(RevocationError::bad_request(
            "EmptyRevocation",
            "provide either `jti` (with `expiresAt`) or `subject`",
        )),
    }
}
}

handle_create_revocation

Each mode goes through the token revoker: revoke_jti or revoke_subject. A jti whose expiresAt has already passed is refused too: the token is already dead, and denylisting it would only leave a dead row.

POST /authorization/revocations, through Scoped<LiveTokenRevoker> (wildflower/Token.d): denylist one token or bump a subject’s epoch. 204 No Content on success; 400 with error and detail for a body that names neither mode, both, a jti without expiresAt, or an expiresAt already past.

#![allow(unused)]
fn main() {
async fn handle_create_revocation(
    tokens: Scoped<LiveTokenRevoker>,
    Json(request): Json<RevocationRequest>,
) -> Result<StatusCode, RevocationError> {
    match request.into_revocation()? {
        Revocation::Token { jti, expires_at } => {
            // Reject an `expiresAt` already in the past: the token is expired
            // (so verification rejects it anyway) and denylisting it just leaves
            // a dead row. A clear 400 surfaces the stale/mistyped value rather
            // than silently no-op'ing. (A too-early-but-future `expiresAt` can't
            // prematurely un-revoke a live token — the store's `purge_expired`
            // retention floor guards that.)
            if expires_at <= Utc::now() {
                return Err(RevocationError::bad_request(
                    "ExpiresAtInPast",
                    "`expiresAt` is in the past; the token has already expired",
                ));
            }
            tokens.revoke_jti(&jti, expires_at)?;
        }
        Revocation::Subject { subject } => tokens.revoke_subject(&subject)?,
    }
    Ok(StatusCode::NO_CONTENT)
}
}

RevocationError

The 400 is this route’s own shape, { "error": …, "detail": … }. A store failure renders as every other /authorization failure does.

Error half of the revocations handler. The request-body validation failures (BadRequest) are HTTP-layer-only — they describe a malformed POST /authorization/revocations body, not a domain outcome — so they can’t live on AuthorizationServerError; the backing-store failures delegate to AuthorizationServerError’s opaque, logged-500 rendering. It is the only /authorization route with an error type of its own; the rest return Result<_, AuthorizationServerError> directly.

#![allow(unused)]
fn main() {
enum RevocationError {
    /// A client-fixable malformed request: JSON 400 of the shape
    /// `{ "error": <error>, "detail": <detail> }`.
    BadRequest {
        /// The refusal's name: `MissingExpiresAt`, `AmbiguousRevocation`,
        /// `EmptyRevocation` or `ExpiresAtInPast`.
        error: &'static str,
        /// A sentence saying what the body should have been.
        detail: String,
    },
    /// A backing-store failure — rendered through `AuthorizationServerError` as the shared
    /// opaque, logged 500.
    Store(AuthorizationServerError),
}
}
